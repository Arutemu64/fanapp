# PWA, offline & sync

> [!NOTE]
> How the app keeps working on a bad or absent connection: the service worker and app shell, the saved (persisted) queries, the queued writes, reachability, and what the screens say about all of it. The decisions behind it are ADRs [0016](adr/0016-workbox-precaching-via-vite-pwa.md)/[0020](adr/0020-workbox-precache-list-from-app-manifest.md) (Workbox), [0021](adr/0021-tanstack-query-for-server-state.md) (TanStack Query + persistence), [0022](adr/0022-createmutation-for-writes.md) (mutations), [0033](adr/0033-indexeddb-persister-without-json.md) (the IndexedDB persister), [0034](adr/0034-client-generated-ids-for-unkeyed-creates.md) (client IDs), and [0038](adr/0038-offline-write-queue-for-idempotent-writes.md) (the write queue). The rest of the frontend lives in [frontend.md](frontend.md).

## Rules at a glance

- **Design for hours offline with short Wi-Fi windows.** That is what a Russian mobile shutdown looks like at a venue ("The network we design for" below): sync fast whenever a window opens, save what attendees need before they leave Wi-Fi, never trust `navigator.onLine`.
- **One answer to "are we online?"** — `reachability` (an active probe), never `navigator.onLine`. It drives TanStack's `onlineManager`.
- **Every API request has a deadline** (`REQUEST_TIMEOUT_MS`, 15s, in `fetchRecordingConnectionFailures`), so a blocked connection fails as "no answer" instead of hanging.
- **A screen works offline only by joining the allowlist** (`OFFLINE_QUERY_KEYS`). Never by default.
- **A write queues only if it is safe to send twice and joins `QUEUED_WRITES`.** Everything else stays online-only and is gated with `offlineWriteGate` (or a page-level online-only state).
- **Bump `QUERY_CACHE_BUSTER` with every breaking change to saved data**, in the same change ("Cache buster" below). A deploy without one keeps the saved cache and the queued writes.
- **Stale data is quiet until it is old enough to mislead.** One "Обновлено …" line, then the warning.
- **User-scoped offline state (saved queries, queued writes) is reset by `Session`** on every identity transition.

## The network we design for

The attendees are in Russia, where mobile internet is routinely cut by region in 2025–2026, most often in the evening and overnight and sometimes for more than a day. During a cut either everything is gone or only a whitelist of approved services keeps working ([Mediazona, Jan 2026](https://en.zona.media/article/2026/01/05/internet); [Mediazona, Apr 2026](https://en.zona.media/article/2026/04/07/russian_internet_censorship_2026), which counts 51–61 regions cut per day and notes that whitelists themselves have failed). Wired broadband and Wi-Fi keep working, so people hop between Wi-Fi spots. Getting this app onto a whitelist isn't a realistic plan: inclusion needs a petition from a federal agency, Russian hosting, and there are no formal criteria ([Право.ру](https://pravo.ru/story/263280/), [iXBT](https://www.ixbt.com/news/2026/04/27/belye-spiski-ne-rezinovye-v-mincifry-objasnili-kak-popast-v-perechen-vebresursov-dostupnyh-pri-otkljuchenii-interneta.html)). Whether Web Push (FCM/APNs) gets through during a cut is disputed and unverified ([Новая газета Европа](https://novayagazeta.eu/articles/2026/03/28/push-ne-proidet), [Хабр](https://habr.com/ru/news/1049512/comments/)), so neither push nor the SSE stream is relied on during one.

What follows from that:

- **The radio stays "connected" while traffic is blocked**, so `navigator.onLine` reads true on a dead network. The active probe is load-bearing.
- **A blocked request may hang rather than fail fast.** The reports don't describe the failure mode, so this is an inference; the request deadline covers it either way.
- **Offline is the normal state for hours**, not an alarm. Notices stay quiet until the data is old ("Stale notices" below).
- **Short Wi-Fi windows are when everything must sync**: the warm-up and the write queue both fire on every recovery and on return to the app.
- **The biggest win is outside the code**: venue Wi-Fi, and signs telling people to open the app on Wi-Fi before they go out.

## Service worker & app shell

The app is an installable PWA: `static/manifest.json` (icons, standalone display) + a service worker (`src/service-worker/index.ts`, its own TypeScript project via `src/service-worker/tsconfig.json`, typechecked by `pnpm check`) that the root layout registers via `registerServiceWorker` (`#lib/utils/serviceWorker.ts`). SvelteKit compiles the worker as an ES module; Workbox handles precaching from a list the worker builds out of SvelteKit's own `$app/manifest` — see [ADR-0020](adr/0020-workbox-precache-list-from-app-manifest.md). SvelteKit's own auto-registration is disabled (`serviceWorker.register: false` in the `sveltekit()` options) because it leaves the `register()` promise's rejection unhandled — a browser that refuses registration (storage-partitioned in-app browsers, private modes, or no module-worker support before Firefox 147) degrades to online-only, which is expected, but surfaced an uncaught "Error: Rejected" to Sentry; our wrapper mirrors SvelteKit's defaults (same script path, `type: 'module'`, registered on `load`) with a `.catch()`. `buildPrecacheManifest` (`#lib/utils/precacheManifest.ts`, unit-tested) turns `immutable` and `assets` into the precache list: the app shell (JS/CSS/fonts, the SVG logo/favicon, `manifest.json`, the PWA icons, the barcode decoder's `.wasm` — [ADR-0032](adr/0032-zxing-wasm-for-camera-scanning.md)) plus the `200.html` fallback. Content-hashed files go in with `revision: null`; `static/` files and `200.html` are revisioned with the build `version`, so they refresh on every deploy. Kept out: responsive raster image sets (runtime-cached instead, see below), `og-image.png` (crawler-only), the rest of `static/` that no offline screen needs (`robots.txt`, the schedule-import template), and the Greek/Vietnamese font subsets a Russian UI never renders. Those subsets still load on demand via `unicode-range`, and offline they fall back to a system font. `latin-ext` stays precached for romaji macrons (ō, ū). `_app/version.json` is never on the list (`$app/manifest` doesn't name it), so SvelteKit's update check always reaches the network. A `NavigationRoute` serves the precached `200.html` shell for navigations, and the SW handles web-push. Pushes arrive as [Declarative Web Push](https://webkit.org/blog/16535/meet-declarative-web-push/) messages (see "Push payload" in [backend.md](backend.md)): Safari 18.4+ Home Screen apps show them without the worker, and the `push` handler only flags the badge there (`event.notification` is set). So on those devices the worker's skip-while-visible doesn't apply and an open app also gets the OS notification, since WebKit revokes the subscription of an imperative handler that shows nothing. `NotificationBell` drops its in-app toast instead when `pushShowsOverOpenApp()` (`#lib/services/pushDevice.svelte.ts`) says this device shows pushes itself (a page-level `window.pushManager`) and is subscribed, so a new notification alerts once either way; the bell count and feed still update. Elsewhere the handler reads the same JSON and shows it itself. It **never caches API requests** — the backend is served under a path on the _same_ origin (e.g. `/api`, derived from `PUBLIC_API_URL`): where the browser supports the [static routing API](https://developer.chrome.com/blog/service-worker-static-routing) (Chrome 123+, Safari 27; not Firefox), an `addRoutes` rule registered at install sends that path straight to the network without starting the worker; elsewhere no route matches it and the navigation fallback denylists it, so API calls still hit the network directly; their user-specific data is cached by the app layer, never the SW. `AppUpdateService` (`#lib/services/appUpdate.svelte.ts`, started by the root layout) polls for a fresh build and, once one is waiting, applies it without a prompt over the screen: the root layout's `beforeNavigate` turns the next link tap to another page into a full load of that page, and until then a dot on the Профиль tab leads to an «Обновить приложение» row on the hub for anyone who wants it now. Every open tab reloads on `controllerchange`; the SW activates the waiting worker only when it receives a `'skipWaiting'` message. OS integration: the manifest declares `shortcuts` (long-press app-icon menu: Программа/Уведомления/Карта) and `launch_handler: navigate-existing` (links into the installed app reuse the open window instead of spawning a duplicate), and the Badging API mirrors the unread-notification count onto the app icon via `#lib/utils/appBadge.ts` — `NotificationBell` syncs the exact count, logout clears it, and the SW push handler sets a count-less "flag" badge that the bell replaces on next open.

- **Failed chunk loads self-recover with a guarded reload.** `hooks.client.ts` listens for Vite's [`vite:preloadError`](https://vite.dev/guide/build#load-error-handling) — a dynamically imported chunk that failed to fetch, typically a boot node dropping on a flaky mobile connection before the SW cached it, or version skew after a deploy removed the old hashed chunk a still-open document points at. SvelteKit already recovers this during client-side navigation, but not on the first load, where it strands the user on the error page (`handleError`). The handler does a full-page reload (the shell is served `no-cache`, see `frontend/nginx.conf`), guarded by a `sessionStorage` timestamp so a genuinely-unreachable chunk falls through to the error page instead of looping, and only when the marker can be persisted — a browser whose storage throws is where an unguarded reload would spin.
- **Responsive image sets are runtime-cached, not precached.** The AVIF/WebP/… variants `<enhanced:img>` emits (the venue maps and the home hero) live in `build`, but precaching a whole set would store every width and format at install when a device only ever displays one — [Workbox's precaching dos-and-don'ts](https://developer.chrome.com/docs/workbox/precaching-dos-and-donts) calls this out specifically. `buildPrecacheManifest` keeps them out of the precache list (it admits no raster format but the PWA icons) and the SW serves them **cache-first at runtime** via a Workbox `CacheFirst` route instead: content-hashed, so a cache hit is never stale; available offline after the first online view; and degrading to each component's own fallback (e.g. `HeroCard`'s branded bed) on a cold-offline first load. The route is bounded by an `ExpirationPlugin` (`maxEntries`/`maxAgeSeconds`, `purgeOnQuotaError`) — unlike the precache it isn't version-cleaned, so the cap is what stops superseded variants piling up across deploys. The SVG logo and favicon stay precached — a single SVG is density-independent, so there's no set to bloat.
- **Workbox runtime only, no PWA build plugin**: the worker imports `workbox-*` for precaching, routing and strategies, but the worker body and its precache list are ours — push, the update handshake, the API bypass, the image runtime cache all stay hand-written (see [ADR-0020](adr/0020-workbox-precache-list-from-app-manifest.md)). Don't add `@vite-pwa/sveltekit` back, switch to `generateSW` or add a `workbox-config.js`: the first does not support SvelteKit 3, and the generic PWA path assumes a fully generated worker that can't host those handlers.
- **Push on this device goes through `PushDevice`** (`#lib/services/pushDevice.svelte.ts`): one capability/permission/subscription/registration flow behind `state` (`on` · `off` · `unknown` · `blocked` · `unsupported`) and `toggle()`, with the browser (`pushBrowser.ts`) and the server injected as ports so it is unit-tested with fakes. Views map `toggle()`'s outcome to copy and never touch `navigator.serviceWorker`; the hub rows use `getDevicePushState()` (browser-only, no network). Reads use `getRegistration()`, not `serviceWorker.ready`, which never resolves without a registered worker.
- **The caching setup is inert in `vite dev`** (the SW guards on `dev` from `$app/env`, and `$app/manifest` lists no build output there anyway), because cache-first assumes the immutable versioned shell only a real build produces. So a service-worker change is **not** testable with `just frontend-dev` — verify it with `just run-prod`. `vite preview` (and so the Playwright suite) won't do either: it serves SvelteKit's output, not the adapter's `build/`, so `200.html` 404s and the worker's install fails. The `push`/`notificationclick` handlers do stay registered in dev.

## Saved data (persisted queries)

- **Offline data is an allowlist of persisted queries**: `OFFLINE_QUERY_KEYS` in `#lib/api/offlineQueries.ts` — the current user (guards, profile), public config (home hero), schedule and subscriptions (programme, "now on stage"), notifications and their unread count, the quest score and standings (`GET /quest`; the leaderboard it carries is what every player already sees), and the player's own award history (`GET /quest/history`). The root load restores them from one IndexedDB entry (`persistQueryClient` + `createIdbPersister` from `#lib/api/queryPersister.ts`: TanStack's IndexedDB persister pattern over `idb-keyval`, which stores the client as an object by structured clone rather than a JSON string, saves throttled to 1s; `QUERY_CACHE_KEY` names the entry, and diagnostics' reset deletes it by that constant) before anything renders, so those screens open offline once they have loaded — no per-page cache code. Queries on the list are saved whenever they hold data (`shouldDehydrateQuery`) — not TanStack's success-only default, because a refetch that failed leaves the query in error with its last good copy, and dropping it would erase the saved programme exactly when the network is bad; every other query is online-only, fetched fresh after a cold start and kept in memory for TanStack's default 5-minute `gcTime`. A screen that must work offline joins by adding its key to the list — never by default, so voting can't show a stale ballot after a restart and the staff tools' data (other people's details) never lands on the device. The cache expires after `CACHE_MAX_AGE_MS` (7 days — a festival weekend plus travel, where the persister's 24h default `maxAge` would drop the programme after a day without opening the app; the listed queries' `gcTime` matches it via `setQueryDefaults`, as the [persistence docs](https://tanstack.com/query/latest/docs/framework/react/plugins/persistQueryClient) require, or unused queries are collected before they are saved). The cache is busted by a hand-bumped constant, not the build ("Cache buster" below). A cache-backed page (schedule, notifications) renders `query.data` whenever it has some. Only the programme (the schedule page and Home's "now on stage") and the quest's score and standings add `StaleDataNotice` (with `cachedAt={query.dataUpdatedAt}`) when the last refetch failed (`isRefetchError`) or reachability is down; how loud it is depends on the copy's age ("Stale notices: quiet first, loud with age" below). The notice is for data that changes under you and where being out of date misleads — acts get moved and skipped, so a cached programme can be wrong and its time lets someone judge it (timestamps "only … when critical", [Google's offline & sync guidelines](https://developers.google.com/open-health-stack/design/offline-sync-guideline)). Append-only data (the notifications feed: a cached copy is incomplete, never wrong, and new items arrive on reconnect, as in a messenger) and the user's own profile go without one; the connection banner covers them, and the profile's write controls explain themselves on tap (`offlineWriteGate`). An installed app also requests persistent storage (`navigator.storage.persist()` in the root layout), so storage pressure can't evict the saved copy before the festival; a browser tab doesn't ask, because Firefox answers that request with a permission popup.

### Cache buster

`QUERY_CACHE_BUSTER` (`#lib/api/offlineQueries.ts`) is `persistQueryClient`'s `buster`: a saved cache whose buster differs is discarded whole on restore, queued writes included. TanStack's docs describe it for changes that "immediately invalidate any and all cached data" ([persistQueryClient, `buster`](https://tanstack.com/query/latest/docs/framework/react/plugins/persistQueryClient)), so it is bumped by hand for those, not tied to the build. Tied to the build `version`, every deploy would wipe the saved programme, and a build applied just before a mobile shutdown (the next link tap applies a waiting one, `AppUpdateService`) would leave the attendee with nothing offline.

**Bump it in the same change as a breaking change to what is saved:**

- a persisted query's response (the `OFFLINE_QUERY_KEYS` endpoints, including DTOs nested in them) loses, renames or retypes a field, or narrows an enum;
- the frontend starts relying on a field the saved copy may lack (a new required field, or an optional one it now reads without a fallback);
- a queued write's request body (`QUEUED_WRITES`) changes the same way, since a saved write replays with its old variables;
- the persisted entry itself changes form (the persister, the dehydrate options).

No bump for an added optional field the UI tolerates missing, a change to an endpoint that isn't saved, a description, or a frontend-only change. Any new string works; the value only has to differ.

### Warm-up: save before the network goes

A screen's data is only saved once something fetched it, so a programme nobody opened before the cut isn't there. `warmOfflineCache` (`#lib/api/offlineQueries.ts`) fetches every allowlisted query the viewer can see — config and schedule for everyone; subscriptions, notifications and the unread count once signed in; the quest score and history while the quest is on — whenever a window opens: at boot, after each login (the root layout watches the user id), on the offline→online edge (`onRecovered`) and on return to the app (`focusManager`). A query fetched within its 60s `staleTime` is skipped and the schedule revalidates by ETag, so a repeat costs a few cheap requests. The feeds are infinite queries whose key carries the page size, so `notificationsFeedOptions()` and `questHistoryFeedOptions()` are shared by the warm-up and the feeds on screen; a mismatch would warm an entry no screen reads. E2E mocks for a signed-in visitor with the quest on must therefore answer `GET /quest` and `GET /quest/history` (`questConfig()` does).

### Stale notices: quiet first, loud with age

In a shutdown region the connection banner says "offline" for hours, so a warning box on every cached screen becomes noise people learn to ignore. Google's offline guideline shows timestamps sparingly, avoids precise times on data more than a day old, and escalates to a prompt only when the device has been offline too long or the user has to act ([Google OHS](https://developers.google.com/open-health-stack/design/offline-sync-guideline)). `StaleDataNotice` follows that:

- **Fresh copy** (younger than `LOUD_AFTER_MS`, 30 minutes, about six to ten acts): one muted line, «Обновлено сегодня в 14:32».
- **Old copy**: the warning `Alert` — what is on screen («Показана сохранённая программа.»), the next step from reachability (offline it promises an update when the connection returns; reachable it says the refresh failed, so a server error is never blamed on the connection), and the sync time. It never restates the cause: offline, `ConnectionBanner` above it already names it.
- The age is read through `minuteClock`, so an open screen turns loud on its own. `LOUD_AFTER_MS` is a tuning knob; change it in one place.
- The quest badge keeps the time in its own stats footer, because a notice under a screen-filling badge would sit below the fold.

## Queued writes

### Write queue

Some writes wait out a lost connection instead of failing ([ADR-0038](adr/0038-offline-write-queue-for-idempotent-writes.md)). A write joins `QUEUED_WRITES` (`#lib/api/writeQueue.ts`) only when sending it twice is harmless:

| Write               | Why a resend is safe                                                                       | Screen             |
| ------------------- | ------------------------------------------------------------------------------------------ | ------------------ |
| Quest award         | client-generated `award_id` (ADR-0034): a replay returns the original award                | `AwardForm`        |
| Subscribe to an act | one subscription per user and act: a replay's `SUBSCRIPTION_ALREADY_EXISTS` counts as done | `SubscribeModal`   |
| Unsubscribe         | targets one subscription: a replay's `SUBSCRIPTION_NOT_FOUND` counts as done               | `UnsubscribeModal` |
| Feedback            | not idempotent, but a duplicate message costs a reader a second look                       | feedback page      |

Votes, profile and account edits, auth and every other staff tool stay online-only (ADR-0022): their state can change while they wait (a voting window closes), or the person needs the answer while the screen is open.

How it works — TanStack's own paused mutations, not a hand-written outbox:

- **Defaults per key.** `registerQueuedWrites` (root load, before the restore) sets `networkMode: 'online'` (the app default is `always`), `retry` for as long as there is no API answer (an API error fails at once), the `mutationFn` and the invalidation. A write restored after a restart has only its key and variables, so it takes all of this from the defaults ([TanStack, persisting offline mutations](https://tanstack.com/query/latest/docs/framework/react/guides/mutations)). Components build their mutation from `queued…Options()` and must not add an `onSuccess`, which would replace the default's invalidation.
- **Pause and hand-off.** Offline (by the probe that drives `onlineManager`) the mutation pauses. `handOffWhenQueued` (`#lib/api/queuedWrite.svelte.ts`) then tells the person when it will go out («Подпишем, когда появится связь»), lets the screen move on, and `reset()`s the observer so the screen's own callbacks never fire for it.
- **Outcome from one place.** `watchQueuedWrites` (root layout) reports how a write that waited ended — a success toast, or the action named alongside the server's reason — wherever the person is by then, even after a restart.
- **Saved and resumed.** Only paused queued writes are persisted (`shouldPersistMutation`); one in flight has already left. After the restore the root layout calls `resumePausedMutations()`, because the online edge that normally resumes them fires only on a change.
- **Shown while waiting.** A queued subscription appears at once on the card, marked «Ждёт связи», through `useQueuedSubscriptionChanges` + `mergeSubscriptions`; unsubscribing it before it leaves cancels it in the queue (`cancelQueuedSubscribe`). The connection banner counts the waiting writes («2 действия ждут отправки»).
- **Quest station offline.** The player lookup needs the server, so offline (or when the lookup gets no answer) a scanned code becomes an `UnverifiedPlayer` — the ID alone, no name or balance — and the award queues; the server checks the ID when it is sent.
- **Reset on identity change.** `Session` drops every waiting write when an account ends (`dropQueuedWrites`), or it would go out under the next person's cookie. A write queued and then logged out of offline is lost, by design.
- **Not Workbox Background Sync.** Safari and Firefox don't support the Background Sync API ([caniuse](https://caniuse.com/background-sync)), and it would put API requests through the service worker, which never handles them. TanStack DB's offline transactions ([docs](https://tanstack.com/db/latest/docs/guides/offline-transactions)) solve a bigger problem than four idempotent writes.

## Screens offline

- **Complete-miss handling (offline vs. failure) — `queryView` + `QueryState`**: a screen read never hand-builds its offline/loading/error/stale chain. `queryView(query, { policy, reachable: reachability.current, errorMessage })` (`#lib/utils/queryView.ts`, pure and table-tested) turns the TanStack result into one of `offline | loading | error{message, retry} | ready{data, stale, cachedAt}`, and `<QueryState view={…}>` (`#lib/components/`) renders the three non-ready branches, so the page writes only a `loading` snippet and its `ready` content (plus `offline` when the screen has its own copy for it). No data plus `!reachable` is offline — a calm inline state that keeps the app shell/bottom nav usable (the query pauses offline, so without it a cold miss would show its skeleton forever). So is a read that got no answer at all while it is still retrying (`isConnectionFailure(failureReason)` with `fetchStatus !== 'idle'`), without waiting for the probe to confirm it. No data while reachable is the skeleton while pending and an inline `ErrorState` once the query has failed; its retry button refetches that query instead of reloading the app. That `ErrorState` shows no «Ошибка N» label: a query rethrows the API body without its HTTP status, so the message (`getApiErrorDetail`, else the screen's `errorMessage`) says what went wrong. A request that got no API answer is retried up to three times first; an API error shows at once. `ready.stale` (the last refetch failed or the server is out of reach) is the cue for a `StaleDataNotice`.
- **Online-only surfaces**: Voting (`voting/+page.svelte`, `voting/[nominationCode]/+page.svelte`) is the read-shaped case: casting a vote is a mutation, and the open/closed and already-voted state must never be shown stale offline (a cached ballot you can't submit is a dead end). Its queries are never persisted, and offline the pages show `OfflineUnavailableState` instead of a copy still in memory from earlier in the session: `queryView`'s `live` policy, where a cached screen uses `cached`. Like every screen read, a read that got no answer counts as offline only while it is still retrying: once the retries stop with the server reachable, nothing reconnects, so the page falls back to `ErrorState` and its retry button. Home hides its voting card offline for the same reason. Pure admin surfaces that fetch nothing use the `offlineUnavailable` flag from their load, shown only while reachability is still down (`data.offlineUnavailable && !reachability.current`) — so the state clears on reconnect without a reload, and a connection that drops while a form is open leaves the form in place. That is the **tools** subtree: `tools/+layout.ts` redirects any online-only tool opened offline to the hub and returns the flag, and the hub lists only the tools that work offline (`worksOffline` in `TOOLS`, `#lib/data/tools.ts` — the quest, whose awards queue), or the online-only state when the person holds none. Feedback is no longer one of these: a message written offline queues ("Write queue" below). Each renders the shared `OfflineUnavailableState` component (`#lib/components/`): one generic screen («Раздел доступен только онлайн»), no props, so no surface writes its own offline copy. It renders in place, never at an `/offline` route. The app shell is precached, so a page load never needs the classic [offline fallback page](https://web.dev/articles/offline-fallback-page). Keeping the URL is what lets the state clear on reconnect without a redirect back, keeps the bottom nav's active tab and deep links intact, and keeps the user in the app ([web.dev offline UX guidelines](https://web.dev/articles/offline-ux-design-guidelines)). A cached screen with nothing loaded yet (the programme, notifications) keeps its own copy, because it promises something different: it will work offline once it has loaded. The quest page is a cached screen: the QR code is built on the device from the cached user, so a player can show it on a dead connection, and the score and leaderboard come from the saved `GET /quest`, flagged with their "synced at" time while stale, since ranks move during the festival: the leaderboard tab takes a `StaleDataNotice`, and the badge prints the time in its own stats footer, because a notice under a screen-filling badge would sit below the fold. The award history is saved too, without a notice: like the notifications feed it is append-only, so a saved copy can lack the newest awards but is not wrong, and a cancellation it has not seen yet also arrives as a notification. Offline with nothing saved, the badge shows the code alone and the other two tabs an inline offline state.
- **Write controls on cached pages degrade, they don't fail (`offlineWriteGate`)**: pages that stay _readable_ offline (profile, schedule) keep the mutations on top of them online-only — but rather than let a tap fail into an error, each write trigger is gated. `offlineWriteGate()` (`#lib/utils/offlineAction.ts`, called at component init) returns a reactive `blocked` and a `guard(handler)`: bind `aria-disabled={gate.blocked}` and wrap the handler (`onclick`, `onsubmit`, `onCheckedChange`). Offline the control dims but stays focusable and tappable, and the tap shows an «Доступно только онлайн» toast instead of acting (the guard also `preventDefault`s, so a guarded submit or link can't fall through to the browser). `aria-disabled`, not `disabled`: a native disabled control can't be focused, swallows the tap and its `title` hint never shows on touch, so the user can't learn why it's dead ([Smart Interface Design Patterns](https://smart-interface-design-patterns.com/articles/disabled-buttons/)). `Button` and `Switch` style `aria-disabled` like `disabled` without `pointer-events-none`; a hand-rolled button adds the `aria-disabled:` classes itself. Keep `disabled` for the other reasons a control is off (a pending mutation). Inputs stay editable offline, so a typed form survives a dropped connection. The same gate covers the submit of the online-only tools forms for a connection that drops after the page opened. A queued write ("Write queue" below) is never gated: offline is exactly when it should be accepted. This is the _mixed read+write_ answer; a surface that is all mutation and opened offline uses the page-level `offlineUnavailable` state above instead.
- **Logout works offline, revoke is queued (`identity`)**: the session lives in an HttpOnly cookie, so JS can't clear it — a purely local logout would let the still-valid cookie silently restore the session on the next `/me`. So `Session.logOut` (called by `LogoutButton` on the Profile page) branches on reachability: online it runs the button's revoke mutation; offline it calls `markLogoutPending()` (`#lib/services/identity.ts`, a persisted intent in `safeStorage`) and tears down local state at once so a shared device stops showing the account: the user query is set to `null`, home replaces the screen, and the session removes every query no screen uses (so the persisted cache stops holding them) and refetches the rest as the guest. The queued `POST /auth/logout` (`flushPendingLogout`) fires from the root layout — on a fresh boot and through the reachability monitor's `onRecovered` callback on the offline→online edge (a boot that is already online never crosses the edge); the monitor itself knows nothing about logout — and is idempotent, so it is one intent, not a write queue. Until it succeeds, the user query's `queryFn` answers `null` while `isLogoutPending()` so a valid cookie can't resurrect the account and there's no "logged back in" flicker. A fresh login cancels the stale intent: `Session.loggedIn` clears it for password/code. A social login returns as a full page load and bypasses `loggedIn`, so its click revokes the old session first (`Session.settlePendingLogout`) and stays on the page if that fails: clearing the intent would let an abandoned OAuth flow restore the old account, and keeping it would let the boot flush end the new session. `loggedIn` also marks the whole cache stale (it was fetched as a guest) and awaits the new identity before navigating, since the guards read it.
- **Identity contract (`currentUserOptions` in `#lib/services/identity.ts`)**: the `/me` query distinguishes three outcomes so a transient error can't silently log a user out: `200` → the user; explicit **`401`/`403`** → `null`, the guest; any **other** failure (`5xx`, network) throws, and TanStack Query keeps the last good user on error. Offline the query pauses and the cached user is served unchanged. The bell clears the OS icon badge in its teardown, the one piece of account state outside the cache.

## Connectivity

- **Every API request has a deadline.** `fetchRecordingConnectionFailures` (`#lib/api/errors.ts`, the generated client's `fetch`) combines the caller's signal with `REQUEST_TIMEOUT_MS` (15s, covering the body read), so a connection that a network blocks without refusing it fails with a `TimeoutError` instead of hanging until the OS gives up on TCP. That error counts as no answer: the query retries, the error interceptor asks the probe, and the offline states take over. TanStack's cancellation signal still works, since the deadline is combined with it (`anySignal`, which falls back to a manual combination before Safari 17.4). The probe, the logout flush and `queryForLoad` keep their own shorter budgets; the SSE stream has its own watchdogs.
- **One reachability state**: `#lib/services/reachability.ts` is the app's single answer to "are we online?" — loads read `isReachable()`, components read the reactive `reachability.current`, and the banner, `ErrorState`, `offlineWriteGate` and the stale notices all agree because they read the same value. It is an active probe of the unauthenticated health endpoint, not `navigator.onLine`, so it stays correct on a captive/dead network that lies about being online; a 502/503/504 counts as unreachable (a live proxy over a dead backend). Only three things write it: the probe, the API client's response interceptor (`watchApiResponses` in `#lib/api/index.ts`, which sees every status), and the SSE handshake. It is also what TanStack Query's `onlineManager` listens to (`reachabilityMonitor` replaces its default `navigator.onLine` listener): while unreachable, queries pause instead of burning their retries, and on the offline→online edge every query on screen refetches (`refetchOnReconnect`) — the catch-up for screens showing cached copies. A request that fails without a response never flips it on its own — the error interceptor asks the probe for a verdict, so one slow endpoint can't take the app offline; **don't call `markReachable` from a `load` or a component**. A probe that would take us _offline_ while `navigator.onLine` is still true — typically the radio still waking as the app foregrounds — keeps re-trying for `OFFLINE_CONFIRM_WINDOW_MS` and only goes offline if none succeed (the transient-fault "let it self-correct before alarming" rule); `navigator.onLine === false` is trusted at once. A probe drops its verdict if fresher evidence landed while it ran — any `markReachable` call counts, even one repeating the current value. `startReachabilityMonitor()` (`#lib/services/reachabilityMonitor.ts`, started from the root layout's `onMount`) re-probes on the browser `online` event and on foregrounding, trusts `offline` as an immediate negative, polls (3s → 30s backoff) only while unreachable so the banner clears on its own, and on the offline→online edge calls the `onRecovered` callback it was started with (the root layout passes the offline-logout flush and the warm-up, `warmOfflineCache`). `ConnectionBanner` shows only this state: "Нет интернета" when `navigator.onLine` is false (the device's own connection), otherwise "Нет связи с сервером" — never blaming the user's internet for a server outage — held for at least `MIN_DISPLAY_MS` (4s) so it never flashes. While down it offers «Повторить», which runs `probeReachability()` at once instead of waiting out the monitor's backoff; on recovery it reads «Обновляем…» while queries on screen are fetching (`useIsFetching({ type: 'active' })` — the stale ones `refetchOnReconnect` reloads and the SSE handshake's catch-up; a screen with nothing to reload skips it), then «Связь восстановлена» for `RESTORED_DISPLAY_MS` before sliding away. The catch-up state is latched, so a later poll can't flip the strip back. Only the text sits in its pre-mounted `role="status"` region, so the button isn't announced as status.
- **Realtime stream (`EventsClient`) is silent to the user**: SSE only carries change signals and every page loads over plain HTTP, so a dropped stream is not shown — it retries in the background with full-jitter exponential backoff capped at `MAX_RECONNECT_DELAY_MS`, never gives up (a stream broken while the backend stays reachable produces no reachability change for anything else to hook), and files one Sentry issue per outage after `REPORT_AFTER_ATTEMPTS`. One watchdog covers each stage: `DIAL_TIMEOUT_MS` for a dial that hangs before headers, `HANDSHAKE_TIMEOUT_MS` for the `connection_established` event, then `HEARTBEAT_TIMEOUT_MS` of silence (the backend emits a named `ping` on idle — see "Realtime (SSE)" in [backend.md](backend.md)). The stream pauses after `HIDDEN_PAUSE_GRACE_MS` in the background (Web Push covers that time), and on foregrounding a stream silent for longer than `STALE_ON_RESUME_MS` is redialled at once — iOS 18 can resume a PWA with its `EventSource` still `OPEN` but dead and never fire `error` ([Apple forums](https://developer.apple.com/forums/thread/765183)). Live events missed during a gap are not replayed, so any handshake after the stream was down invalidates the whole query cache — what is on screen refetches, the rest when next shown. A return from the background pause needs no catch-up of its own: foregrounding already refetches every query on screen (TanStack's `refetchOnWindowFocus` — all stale by then, since the pause grace outlasts the 60s `staleTime`), which also covers a proxy that blocks SSE while HTTP works. `getEventsClient()` returns a non-nullable client — the root layout always constructs one (`setEventsClient(queryClient)`) — so subscribe with `eventsClient.on(...)`, not `?.on(...)`. **Data never listens to `connection_established`** — that handshake is the client's own business. Domain events (`schedule_updated`, `config_updated`…) are mapped to query keys once, in the root layout; a component subscribes only for something that isn't data (the bell's push toast, the notifications page's screen-reader announcement).

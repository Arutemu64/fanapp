# Transactional Outbox — Design & Implementation Plan

## 1. The problem

The aggregate-event path is a **dual write**. `SqlUnitOfWork.commit()` (`adapters/db/uow.py`) commits the DB transaction and *then* publishes domain events to NATS:

```python
async def commit(self) -> None:
    await self.session.commit()      # 1. transaction durable
    await self._dispatch_events()    # 2. publish to NATS — a separate system
```

If the process dies (or NATS is down) between step 1 and step 2, the state change is persisted but the event is **lost forever**. Your own `backend.md` already flags this and names the `UnitOfWork` as the fix site.

## 2. The principle: outbox covers aggregate events only

The codebase already splits events into two kinds, and that split *is* the boundary:

| Event kind | Today | After |
|---|---|---|
| **Aggregate events** — recorded via `record_event()`, dispatched by the UoW (`VoteCreated`, `ScheduleChangeCreated`) | commit, then publish (dual write) | written to the **outbox table in the same transaction**, delivered by a relay |
| **Service events** — published directly via `EventBroker`, tied to no committed state (`NotificationQueued`, `BroadcastQueued`, email codes) | direct to NATS | **unchanged** — still direct, fire-and-forget |

Service events are left alone — several run with no DB write at all, so forcing a commit just to flush an outbox row would be ceremony with no consistency to protect. This is exactly the "commit for nothing" you didn't want, and we avoid it by respecting a boundary the codebase already drew.

## 3. Architecture

```
write request                          outbox relay (interval job in scheduler)
─────────────                          ────────────────────────────────────────
interactor                             IntervalTrigger (~1–2s)
  └─ aggregate.record_event()            └─ PublishOutboxEvents
  └─ uow.commit()                            ├─ OutboxGateway.fetch_unpublished()  SELECT … FOR UPDATE SKIP LOCKED
       ├─ session.add(OutboxEventORM)        ├─ EventBroker.publish_raw(subject, payload, msg_id) → NATS
       └─ session.commit()  ◄── atomic       └─ OutboxGateway.mark_published(ids) + commit
```

- **Writer = the `UnitOfWork`** — stops publishing; serializes each pulled aggregate event into an `OutboxEventORM` row added to the session *before* `session.commit()`. Drops its `EventBroker` dependency entirely.
- **`EventBroker` keeps its single `NatsEventBroker`** everywhere — no DI swap, no second adapter.
- **Relay = an interval job inside the existing scheduler service** — no new process. Polling latency is owned by APScheduler's `IntervalTrigger` (seconds), not by `CronTrigger`, so sub-minute delivery works fine. The `FOR UPDATE SKIP LOCKED` read keeps it safe to extract into its own process later with zero logic changes if load ever demands it.

## 4. Implementation steps

### 4.1 Schema

Migration `009_add_outbox_table.py` (hand-numbered, not autogenerated) + `adapters/db/models/outbox.py` → `OutboxEventORM` (registered in `models/__init__.py`):

| Column | Type | Notes |
|---|---|---|
| `id` | `Uuid` PK, `uuid7` + `gen_random_uuid()` server default | also the NATS dedup id |
| `subject` | `Text` | `event.subject` |
| `payload` | `JSONB` | `event.model_dump(mode="json")` |
| `created_at` | `timestamptz` | from `BaseORM` |
| `published_at` | `timestamptz` null | `NULL` until delivered |

Plus a **partial index** `WHERE published_at IS NULL` ordered by `created_at` — keeps the relay's hot set tiny regardless of table size.

### 4.2 Writer

`adapters/db/uow.py`:

```python
class SqlUnitOfWork(UnitOfWork):
    def __init__(self, session: AsyncSession) -> None:   # EventBroker removed
        self.session = session
        self._tracked: dict[int, AggregateRoot] = {}

    async def commit(self) -> None:
        self._store_events()             # add OutboxEventORM rows
        await self.session.commit()      # domain + outbox committed atomically

    def _store_events(self) -> None:
        for entity in self._tracked.values():
            for event in entity.pull_events():
                self.session.add(
                    OutboxEventORM(subject=event.subject,
                                   payload=event.model_dump(mode="json"))
                )
        self._tracked.clear()
```

No registry needed to re-emit — republishing the stored JSON to `subject` is byte-identical to publishing the typed event, so FastStream subscribers deserialize it unchanged. Update the `SqlUnitOfWork` provider in `main/ioc/db.py` to drop the broker arg.

### 4.3 Relay read side

- Port `application/ports/repositories/outbox.py` → `OutboxGateway`: `fetch_unpublished(limit)` + `mark_published(ids)`; small `OutboxMessage` DTO (`id`, `subject`, `payload`).
- Adapter `adapters/db/gateways/outbox.py` — `SELECT … FOR UPDATE SKIP LOCKED` ordered by `created_at` (concurrency-safe, no double-send).
- `EventBroker` gains `publish_raw(subject, payload, message_id)`; `NatsEventBroker` sets `message_id` (row id) as `Nats-Msg-Id` → **JetStream dedup** within its window.
- Interactor `application/interactors/outbox/publish_outbox_events.py` — fetch batch → `publish_raw` each → `mark_published` → commit.

### 4.4 Relay runtime (interval job in the scheduler)

No new process. Register the relay as an `IntervalTrigger` job in the existing scheduler (`main/scheduler.py`), reusing the current `make_interactor_job` helper:

```python
scheduler.add_job(
    make_interactor_job(container, PublishOutboxEvents),
    IntervalTrigger(seconds=config.outbox.poll_interval_seconds),
    id="outbox_relay",
    max_instances=1,   # never overlap a slow tick with the next
    coalesce=True,     # collapse missed ticks into one
)
```

The existing cron loop (which skips jobs with `cron=None`) is unchanged; the relay is registered alongside it as an interval job rather than going through `get_job_definitions`. No new container, CLI entry, or DI container is required.

> **Tradeoff (accepted):** the relay shares the scheduler's process/failure domain. `AsyncIOScheduler` runs jobs concurrently on the event loop, so as long as the sync jobs (`SyncTCloud`, `SyncCosplay2`) actually `await` their I/O, they won't block the relay; `max_instances=1` + `coalesce` stop the relay piling up on itself. Acceptable at this app's scale, and extraction into a dedicated process later is a *move*, not a rewrite.

### 4.5 Config

`outbox` section: `poll_interval_seconds` (~1–2s), `batch_size`.

### 4.6 Retention

APScheduler cron in `presentation/scheduler/jobs.py` deleting `published_at < now() - N days`.

## 5. Delivery guarantees

- **Atomicity** — domain write + event commit together or not at all.
- **At-least-once** — relay retries until marked published; consumers stay **idempotent** (they already key on `vote_id`/`mailing_id`), with `Nats-Msg-Id` dedup as backstop.
- **Latency** — events arrive within one poll interval (~1–2s). **SSE/realtime unaffected** — it uses `RealtimeGateway`, not `EventBroker`, and never touches the outbox.

## 6. Optional follow-up: promoting service events

Three service events publish *after* a real commit and would silently no-op if lost — candidates to record on their aggregate (→ outbox) if you want the guarantee. Out of scope for the first pass, your call:

| Site | Event | Risk if lost |
|---|---|---|
| `send_broadcast.py:53` | `BroadcastQueued` | a created mailing never sends |
| `cancel_mailing.py:50` | `MailingCancelled` | a cancelled mailing keeps sending |
| `send_schedule_change_notifications.py:226` | schedule notifications | subscribers miss a change |

Truly ephemeral ones (`send_test_notification`, email-code resends) stay direct.

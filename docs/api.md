# API Integration Guide

This guide details best practices for using `@hey-api/openapi-ts` (SDK, types, and TanStack Query options) and `@tanstack/svelte-query` in the SvelteKit frontend to achieve type-safe communication with the FastAPI backend and clean per-request state isolation. The frontend is a client-rendered SPA, so the browser talks to the backend directly.

The shape of this stack — what replaced `openapi-typescript` + `openapi-fetch`, the traps found migrating the first pages, and what's still open — is recorded in
[docs/sketches/hey-api-tanstack-query-migration.md](sketches/hey-api-tanstack-query-migration.md).

---

## Core Concept: Single Source of Truth

- **Generated SDK, types & query options**: `frontend/src/lib/api/client/` (generated by `@hey-api/openapi-ts`, config in `frontend/openapi-ts.config.ts`) is the single source of truth for API contracts — SDK functions (`getSettings`, `updateSettings`, …), TypeScript types (`SettingsDto`, `ErrorMessage`, …), and TanStack Query options (`getSettingsOptions`, `updateSettingsMutation`, …).
- **Auto-generation**: Run `just frontend-generate-api` from the workspace root whenever the backend endpoints, routers, or Pydantic schemas change.
- **Plugins**: `@hey-api/client-fetch` (transport), `@hey-api/typescript` (types), `@hey-api/sdk` (plain request functions), `@tanstack/svelte-query` (query/mutation options built on the SDK). Configured in `openapi-ts.config.ts`.

### Both generated artifacts are enforced in CI

Forgetting to regenerate is not a silent failure — two committed artifacts each have a check, because a stale one still compiles and would quietly disarm every guard below.

| Artifact                       | Generated from       | Checked by                                                                             |
| ------------------------------ | -------------------- | -------------------------------------------------------------------------------------- |
| `shared/openapi/openapi.json`  | the routers and DTOs | `backend/tests/unit/presentation/test_openapi_spec.py` (runs with `just backend-test`) |
| `frontend/src/lib/api/client/` | that spec            | `just frontend-check-api` (`pnpm generate-api:check`; its own CI job)                  |

`just frontend-generate-api` regenerates both and fixes either failure. `@hey-api/openapi-ts` has no built-in `--check` flag (unlike the old `openapi-typescript`), so `frontend/scripts/check-generated-api.mjs` regenerates into a throwaway directory and diffs it against the committed one.

**`info.version` is compared separately, against `pyproject.toml`.** It is the one field in the spec whose value comes from outside the repo: `APP_VERSION` reads the _installed_ distribution metadata, so a stale editable install (common right after a release bump, before `uv sync`) makes it disagree with `pyproject.toml` and would fail a whole-document comparison over a field that has not drifted. The spec test therefore renders with the version the committed file already carries — leaving every other byte compared — and a second test checks `info.version` against `pyproject.toml`. Both of that test's inputs are committed files, so it gives the same answer on a laptop, in CI, and in a cloud session.

The general rule when adding to the spec: **a value that is not derived from committed source does not belong in a committed artifact.** `APP_BUILD` (the commit SHA) is the reason this matters — putting it in `info` would churn the spec, and the generated client with it, on every single commit. Keep build- and environment-derived values on a runtime endpoint (`/debug/`) instead, and if one has to be in the spec, give it its own test against its own source of truth rather than the byte comparison.

## Client Isolation

A shared module-scoped client is fine here _only_ because it is a stateless transport: `lib/api/client-config.ts` configures the one hey-api `client` (base URL, `credentials: 'include'`, the reachability and session-expiry interceptors — see below) once at module load, and every generated SDK/query function reaches for that same client by default. That is safe precisely because the client itself carries no per-user data — no in-flight request state, no cached response. Never reintroduce per-context client construction; there is nothing left to isolate at that layer.

The rule this guide's title refers to (docs/frontend.md §1, "never keep request- or user-scoped state in a frontend module singleton") now applies one layer up, to the **query cache**: `lib/api/queryClient.ts` exports a module-singleton `QueryClient` for the same reason `cacheStore` in `offlineCache.ts` is one — a shared cache is the point. Isolation across login/logout is achieved by clearing the user-scoped **query keys** on logout (mirroring `clearUserCache()`), not by recreating the client. See `queryClient.ts`'s own doc comment for the reasoning and the obligation this places on the next query that caches per-user data.

### 1. Universal load functions (`+page.ts` / `+layout.ts`)

Call the generated SDK function directly, passing SvelteKit's `fetch`:

```typescript
import { getSettings } from "$lib/api/client";
import type { PageLoad } from "./$types";

export const load: PageLoad = async ({ fetch, depends }) => {
  depends("app:settings");

  const { data, error, response } = await getSettings({ fetch });

  if (error || !response.ok) {
    // Handle/log error...
  }

  return { settings: data };
};
```

A page that wants the query cache warmed before it blocks-loads (so its component's `createQuery` reads a populated cache on mount, per docs/frontend.md §4 "Section loading") uses the generated query options with the shared `queryClient` instead:

```typescript
import { getSettingsOptions } from "$lib/api/client";
import { queryClient } from "$lib/api/queryClient";
import type { PageLoad } from "./$types";

export const load: PageLoad = async ({ fetch }) => {
  await queryClient.ensureQueryData(getSettingsOptions({ fetch }));
  return { title: "Настройки фестиваля" };
};
```

> [!IMPORTANT]
> **Why inject the SvelteKit-provided `fetch` in load functions?**
>
> - **Request deduplication**: SvelteKit dedupes identical requests and lets `invalidate()` re-run the load when its data changes.
> - **Relative URL Resolution**: SvelteKit resolves relative routes correctly.
> - **Cookies**: The `session_id` cookie is carried automatically by the browser; the client uses `credentials: 'include'` and the frontend is served same-origin with the API (behind Caddy), so it stays first-party.

### 2. Browser & Svelte Component Context

For local component scripts (`.svelte`), call the SDK function directly for a one-off request, or `createQuery`/`createMutation` (options as a **thunk**, `() => ({...})` — required for reactivity on `@tanstack/svelte-query` v6) to read from the shared cache:

```svelte
<script lang="ts">
	import { listUserNotifications } from '$lib/api/client';
	import { onMount } from 'svelte';

	let notifications = $state([]);

	async function loadNotifications() {
		const { data } = await listUserNotifications({ query: { limit: 10 } });
		if (data) notifications = data.notifications;
	}

	onMount(() => {
		void loadNotifications();
	});
</script>
```

```svelte
<script lang="ts">
	import { getSettingsOptions, updateSettingsMutation } from '$lib/api/client';
	import { createMutation, createQuery, useQueryClient } from '@tanstack/svelte-query';

	const queryClient = useQueryClient();
	const query = createQuery(() => getSettingsOptions());
	const mutation = createMutation(() => ({
		...updateSettingsMutation(),
		onSuccess: () => queryClient.invalidateQueries({ queryKey: getSettingsQueryKey() })
	}));
</script>
```

## TypeScript Type Extraction

The generated `src/lib/api/client/types.gen.ts` exports every schema, request, and response type by name directly — no indexed-access lookup needed. Re-export or alias what a module needs:

```typescript
import type { NotificationDto } from "$lib/api/client";

export type NotificationDTO = NotificationDto;
```

Request/response shapes for one operation are named `<OperationName>Data` / `<OperationName>Response` / `<OperationName>Error`:

```typescript
import type {
  UpdateSettingsData,
  UpdateSettingsResponse,
} from "$lib/api/client";

// UpdateSettingsData['body'] is the PATCH /settings request body.
// UpdateSettingsResponse is its success payload.
```

### Enum schemas are the single source of truth

Backend `StrEnum`s that appear on a DTO field (`UserRole`, `Permission` in `core/vo/`) are emitted as OpenAPI enum schemas, so `frontend-generate-api` regenerates them as string-literal unions (`Permission`, exported directly from `$lib/api/client`). Never hand-copy enum values on the frontend — derive them. Permission literals in `lib/utils/permissions.ts` are typed as `Permission = PermissionGen` (aliasing the generated type), so a backend rename/removal makes the stale literal fail `pnpm check` instead of silently breaking permission checks (same drift-guard idea as the error `code` union below). To expose a new enum on the wire, type a DTO field with the enum (not a plain `NewType` str) and run `just frontend-generate-api`.

## Mutations & Data Recovery

- **UI Consistency**: Define how the UI becomes consistent after mutations (e.g. `invalidateQueries`/`invalidate` on the affected key, optimistic update, or full state refetch).
- **Dependency Invalidation**: A page still on plain `load` + `depends(...)` triggers a refresh with `invalidate('app:something')` after a successful mutation, same as before. A page on `createQuery` invalidates its TanStack query key instead (`queryClient.invalidateQueries({ queryKey: getXQueryKey() })`), from the mutation's `onSuccess`.
- **Return Checking**: A direct SDK call returns `{ data, error, response }` (like `openapi-fetch` did) — check all three. A TanStack query/mutation option sets `throwOnError: true` internally, so its `queryFn`/`mutationFn` **throws** the parsed error body instead — see `throwHeyApiError` below.

### Long-running actions (202 Accepted)

An action that cannot finish inside the request returns **202** with the created record and a `Location` header pointing at a **status resource** the client re-reads, instead of blocking. `POST /sync/{source}` is the first of these: it queues the work, returns the `SyncRunDto`, and sets `Location: /sync/sources`.

- **The status resource is an existing list endpoint, not a per-run one.** `GET /sync/sources` already reports each source's latest run, including the active one, so a dedicated `GET /sync/runs/{id}` would exist only to satisfy the convention. Add a per-run endpoint if something genuinely needs to poll one run by id — not before.
- **Prefer SSE over polling for progress.** The page subscribes to the relevant `SSEEventName` (here `sync_run_updated`) and calls `invalidate(...)`; it also re-invalidates on `connection_established`, so an update missed while the stream was down (or the tab was backgrounded past the pause grace) self-heals on reconnect rather than leaving a stale "in progress" on screen. Treat the SSE payload as a nudge to refetch, never as the source of truth.
- **A second request while one is running is a 409**, mapped to Russian copy by `code` like any other error — not a silent no-op.

## Russian Localization & Error Handling

Russian copy is mandatory (AGENTS.md, "Never"). API-specific rule: normalize failures before presenting them — never expose raw backend stack traces or internal identifiers, and show a friendly Russian message explaining how to recover or retry.

- **Error shape**: every error response is `ErrorMessage { code, details }` (see backend `presentation/web/exceptions.py`). Map failures by the machine-readable `code`, not by HTTP status or message text.
- **Single funnel, transport-agnostic**: `getApiErrorDetail(error)` (`lib/api/errors.ts`) turns a payload into Russian copy by duck-typing `{code, details}` off of it — it doesn't care which client produced the error. For **mutations/toasts** use `toastService.error(err)`. For a **`load` failure from a direct SDK call** (which still returns `{data, error, response}`, a real `Response`) use `throwApiError(apiError, response, fallback)`. For a **`load` failure from a TanStack query** (`queryClient.ensureQueryData(...)`, which throws instead) use `throwHeyApiError(apiError, fallback)` — same funnel, but reads `status` off the thrown error object itself rather than a `Response`, because `lib/api/client-config.ts`'s error interceptor stamps it there (see the next point). Either throws a SvelteKit `error()` with the mapped copy and the real HTTP status (and carries `code` on `App.Error`), so a load failure looks like every other error instead of a bespoke per-page string. Add new copy to the `ERROR_MESSAGES` dictionary in `errors.ts`. (Permission guards and offline-cache-miss states still throw `error()` directly — they have no API `code` to map.)
- **Why the error carries `status` at all**: a TanStack query/mutation option's `queryFn`/`mutationFn` sets `throwOnError: true`, and hey-api's client then throws the parsed error body _alone_ — no `Response` travels with it. A call site that needs the HTTP status for branching (401/403/404/422 → distinct Russian copy) would have nothing to read it from, so `lib/api/client-config.ts` registers a global `client.interceptors.error.use(...)` that stamps `status` onto the thrown object once, for every consumer.
- **`code` is a typed union**: the backend stamps the closed set of client-facing codes onto `ErrorMessage.code` as an OpenAPI enum (`presentation/web/error_codes.py`), so `frontend-generate-api` regenerates it as a string-literal union on the generated `ErrorMessage` type. Dictionary keys are checked against it — a typo is a compile error.
- **Drift guard**: a compile-time exhaustiveness check in `errors.ts` fails `pnpm check` if the backend adds a client-facing code that is neither given copy nor listed in `GENERIC_FALLBACK_CODES`. After changing backend error codes, run `just frontend-generate-api` and resolve any new code the guard reports.

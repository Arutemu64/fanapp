# Backend Architectural Guidelines

> Testing conventions (unit vs integration, what to fake, rollback isolation)
> live in [testing.md](testing.md).

> Layer boundaries are enforced: `just backend-import-lint` (import-linter, config in `backend/pyproject.toml`) fails the build if `core/` imports any outer layer, or if `application/` imports `adapters/`/`presentation/` outside the sanctioned exceptions listed below. Run it after touching imports; it is part of `just backend-lint`.

## Rules at a glance

Everything below this section is detail; these rules alone prevent most mistakes.

1. `core/` is pure domain: plain dataclasses, no I/O frameworks. Pydantic is allowed
   only in `core/events/base.py` and `core/vo/fields.py`.
2. `application/` orchestrates through ports (`application/ports/`) — never ORM
   models or concrete adapters.
3. One gateway port per aggregate (`XGateway`): writes first, then `read_*` DTO
   projections under a `# Read projections (return DTOs, not aggregates)` divider.
4. Ports are `typing.Protocol` (no `@abstractmethod`); adapters explicitly subclass
   their port so the type checker catches signature drift.
5. Authorize via `PermissionService.ensure(...)` — never hardcoded role checks.
   Authenticate inside interactors via `CurrentUserProvider.require_user()` — never
   FastAPI `Depends`.
6. Commit only via `uow.commit()`. A fact: `record_event()` inside the aggregate.
   An instruction to do work later: a `Command`, `uow.enqueue()`d in the
   interactor. Both are delivered through the outbox ([ADR-0040](adr/0040-commands-separate-from-domain-events.md)).
7. Translate known `IntegrityError`s to domain exceptions at the gateway with
   `translate_integrity_error` — do not pre-`SELECT` to dodge the race.
8. New domain exception: inherit the semantic marker (`NotFound`, `Conflict`, …)
   listed _first_ in the bases; never edit the status map.
9. Migrations: prefer autogenerate; always review the output (renames emit as
   drop+create; enum member changes need hand-written migrations).
10. Logging: stdlib `logging.getLogger(__name__)`; short static message + scalar ids
    in `extra`; `str(...)` UUIDs; never log secrets, codes, or PII.
11. A create with no natural key whose duplicate does harm takes a client-generated
    UUIDv7 (`UuidVersion(7)` on the input). Replay the same caller and payload
    as success; raise a `Conflict` otherwise, and map `pk_<table>` for the race
    ([ADR-0034](adr/0034-client-generated-ids-for-unkeyed-creates.md)).
12. Wire schema names are the class names, so the suffix says what a model is: an
    application DTO taken as the request body as-is is `…Input`; a route's own
    JSON body, needed because the `…Input` also carries a path param or the
    client IP, is `…Body` (`MoveScheduleEventBody`); a form or multipart body
    is `…Form`; a read model is `…DTO`, and an interactor's own result wrapper
    `…Output`.
    Every response field is required, nullable when it can be empty — no
    defaults on response DTOs (guarded by `test_openapi_spec.py`).
    A person on a record is a `UserRefDTO` in a field named for their role
    (`user`, `awarded_by`, `created_by`, `used_by`), null when nobody is, and
    never a flat `x_user_id` + `x_username` pair; several people are several
    such fields, or a list of refs. A recipient that is always the caller stays
    out of the response (`Field(exclude=True)` when the code still needs it).

## Common task recipes

### Add a persisted aggregate

1. Domain model in `core/models/` (dataclass; subclass `AggregateRoot` if it records events).
2. ORM model in `adapters/db/models/` — storage types only, no VO-typed columns.
3. Port `XGateway` in `application/ports/gateways/`; implementation in `adapters/db/gateways/` explicitly subclassing it, with module-level `_to_model`/`_from_model`/`_parse_*_dto` functions above the class — the only place VO ↔ storage conversion happens. If the aggregate records events, call `self.uow.register(aggregate)` in every `add`/`get`.
4. Wire providers in `main/ioc/`; generate a migration (`just backend-generate-auto <name>`) and review it.

### Add a domain event or a command

1. A fact an aggregate records → class in `core/events/<context>.py`, subclassing `DomainEvent`; PascalCase past tense (`ScheduleChangeCreated`); `subject` `<context>[.<entity>].<past-verb>` (`schedule.change.created`). Raise it with `record_event()` inside the aggregate method; the outbox delivers it on `uow.commit()`.
2. An instruction to do work later → class in `application/commands/<context>.py`, subclassing `Command`; `<Imperative><Subject>Command` (`CreateNotificationCommand`); `subject` `cmd.<context>[.<entity>].<verb>` (`cmd.notifications.create`). Send it with `self.uow.enqueue(...)` before `uow.commit()`; only a consumer that is itself redelivered publishes one directly via `EventBroker`.
3. Add a FastStream subscriber on the JetStream `stream` in `presentation/faststream/routes/` — never add a published message without a subscriber. This rule is load-bearing: the stream only carries subjects its subscribers register, so a message nobody subscribes to fails every publish and its outbox rows retry forever. `tests/unit/presentation/test_event_subscribers.py` fails the build on an orphaned event or command. Declare it with `config=consumer_config()` and `ack_policy=AckPolicy.NACK_ON_ERROR` (or `MANUAL`), never the default — see [Consumers: acks and redelivery](#consumers-acks-and-redelivery).
4. `subject` is a published contract: renaming one is a migration, not a rename.

### Add a client-facing domain exception / error code

1. Define the exception with the semantic marker first in its bases (`class UserNotFound(NotFound, UserException)`).
2. If it never reaches an HTTP client, list it in `INTERNAL_ONLY` in `tests/unit/presentation/test_exception_status_map.py` — the drift test fails otherwise.
3. Run `just frontend-generate-api`, then add Russian copy for the new code to `ERROR_MESSAGES` in `frontend/src/lib/api/errors.ts` (a compile-time exhaustiveness guard reports it until you do).

### Add an SSE event

1. Add a member to `SSEEventName` (`application/dto/realtime.py`) — snake_case, single token, **no dots**.
2. Mirror it in `SSEEventMap` (`frontend/src/lib/services/events.svelte.ts`) — the two are kept in sync by hand.

### Change the schedule-import spreadsheet format

The columns an organizer must supply are named in three coupled places — change one, change all three:

1. `REQUIRED_COLUMNS` in `adapters/parsers/schedule.py`, the only authority. Reject a bad file with `InvalidScheduleFile` carrying a `reason` plus the column/row that located it, so the frontend can name the cell instead of saying "bad file".
2. The downloadable template, regenerated with `just backend-generate-schedule-template` (script: `scripts/generate_schedule_template.py`, output: `frontend/static/schedule-template.xlsx`). `tests/unit/adapters/test_schedule_parser.py` parses the committed file, so a forgotten regeneration fails there rather than reaching an organizer.
3. The on-screen column list in `frontend/src/routes/(app)/(protected)/tools/schedule/components/FileFormatGuide.svelte`.

Every column must appear in the header. A row is either an **event** or a
**block start** (ADR-0026), told apart by `type`: blank or `event` for an event,
`block` for a block start whose `title` names the block. A block row must leave
`number`, `duration` and `nomination_title` blank (`BLOCK_ROW_WITH_EVENT_DATA`
otherwise), and any other `type` is `INVALID_TYPE`. Every event belongs to the
block row above it. On an event row `number` may be left empty: breaks and other
filler rows carry no public number, so `ScheduleEntry.number` is `int | None`
all the way out to the API. `number` is also the only identity an event row has,
so `ImportSchedule` can match a numberless row to nothing — it is imported as a
**new** event, and the numberless events already in the schedule are deleted as
orphans like any other row missing from the file. Block rows are matched by
title.

## Core Domain & Interactors

- **Core Layer (`core/`)**: Pure domain entities, value objects, and domain exceptions. Must be free of all I/O frameworks and outer layers — no FastAPI, SQLAlchemy, no `adapters/`/`application/`/`presentation/` imports. **Pydantic is the one allowed exception, and only in two narrow spots**: `core/events/base.py` (`Message`, the base of domain events and commands, is a `BaseModel` so they serialize cleanly over NATS) and `core/vo/fields.py` (validation helpers for value objects). Do not reach for Pydantic elsewhere in `core/` — plain dataclasses are the default for entities and value objects.
- **Application Layer (`application/`)**: Orchestrates interactors and business use cases. Must never import database ORM models directly. Communication with infrastructure happens via abstract interfaces (ports under `application/ports/`) and schemas/DTOs.
- **One gateway port per aggregate**: Each aggregate has a single port under `application/ports/gateways/`, named `XGateway`, that carries both writes (loading and persisting aggregates) and reads (DTO projections returned to callers). Group the read methods at the bottom of the port under a `# Read projections (return DTOs, not aggregates)` comment and prefix them with `read_`. These are **gateways, not repositories, on purpose** — they also serve read DTOs, and we deliberately do **not** split reads into separate CQRS-style query ports; the rationale and the conditions for revisiting live in [ADR-0003](adr/0003-persistence-gateways-over-repositories.md).
- **Ports are `Protocol`, never `ABC`**: Define every port in `application/ports/` as a `typing.Protocol`; do not decorate port methods with `@abstractmethod`. Adapters in `adapters/` **must explicitly subclass** the port they implement (e.g. `class SqlUserGateway(UserGateway): ...`), so `just backend-typecheck` (`ty`) flags any method that drifts from its port — missing method, changed parameters, or a changed return type. Rationale: [ADR-0005](adr/0005-ports-as-protocol-with-explicit-adapter-subclassing.md). The same applies to test doubles, which `ty` checks too — see [docs/testing.md](testing.md) "Test doubles subclass what they stand in for".

## Services

Services hold logic that is reused across several interactors (or is too cohesive to scatter through them). An interactor is one use case end-to-end; a service is a focused collaborator the use case leans on. Use a service only when the logic is genuinely shared — a single-caller helper usually belongs inline in its interactor. Services are wired in `main/ioc/services.py` (request-scoped). There are two homes, chosen by what the service depends on:

- **`core/services/`** — **pure** domain logic with no ports and no I/O (e.g. `email_login.py`: OTP policy constants plus a code generator). Same purity rules as the rest of `core/`: no FastAPI, SQLAlchemy, Pydantic, or adapter imports. These need no DI wiring when they are plain functions.
- **`application/services/`** — services that orchestrate over **ports** (gateways, id-provider, etc.). They live in the application layer precisely because they touch infrastructure through abstract ports — never concrete adapters or ORM models.

Naming: suffix services with `Service` (the historical `CurrentUserProvider` is the one exception). A port-dependent collaborator that is really an infrastructure concern (password hashing, etc.) is **not** a service — model it as a port in `application/ports/` with an adapter in `adapters/`, so the application layer stays free of concrete libraries.

### Authorization

Gate use cases through `PermissionService.ensure(user, Permission.X)`, never with hardcoded role checks (`if user.role is UserRole.ORGANIZER: ...`). `UserRole` (`visitor`/`participant`/`volunteer`/`organizer`) is just a label — it drives UI grouping (e.g. which nav sections a user can discover) but grants no access by itself, including for `ORG`. Every permission (the `Permission` enum in `core/vo/permission.py`, backed by a CHECK constraint on `user_permissions.permission` — adding a member needs a migration) must be explicitly granted to a user via a `user_permissions` row before `ensure` lets them through; there is no role-based bypass. Genuine ownership-or-permission checks (e.g. "the owner, or anyone with `notifications:send`") keep the ownership comparison inline and fall back to `ensure` only for the non-owner branch.

The one grant that is not a specific capability is the wildcard `*` (`Permission.WILDCARD`): a user holding it passes every `ensure(...)` check, so a single grant covers all organizer surfaces (bootstrap, dev, single-admin deploys). It is an ordinary storable member — granted/revoked through the same CLI and CHECK constraint as any other — and `*` short-circuits only at check time (`PermissionService.ensure`, and the frontend `hasPermission`). It is a superuser grant, so hand it out sparingly; prefer specific grants for day-to-day organizers. Note that audience queries which filter on a _specific_ permission (e.g. `read_schedule_editors` selecting `schedule:manage` holders) do not treat `*` as a match — the wildcard governs authorization, not notification targeting.

**Unattended interactors authorize too.** An interactor invoked only by cron, the CLI or a NATS consumer still calls `ensure(...)` — it does not get to skip the check just because no human triggered it. Those entrypoints all build `create_system_container()` (`main/cli.py`, `main/worker.py`), so `require_user()` resolves to the seeded **system user** (`SYSTEM_USER_ID` in `core/vo/user.py`, served by `adapters/auth/providers/raw.py`), which is granted the one permission it needs by migration — least-privilege, exactly like any other user, with no special-casing in `PermissionService`. `ExecuteCosplaySync` / `ExecuteTicketsSync` and the `sync:run` grant are the worked example. This matters because there is no authorization gateway here: the interactor _is_ the trust boundary, so an unchecked interactor is an unguarded entry point waiting for someone to wire a route to it. The cost is that dropping the grant silently disables the automation, so an integration test asserts the system user holds it (`tests/integration/sync/test_execute_sync.py`).

Authentication is **enforced inside interactors**, not via FastAPI `Depends`: the current user is resolved through `CurrentUserProvider.require_user()` (`application/services/current_user.py`), backed by the `IdProvider` port (the web adapter reads the session cookie in `adapters/auth/providers/web.py`). FastAPI therefore can't infer which routes need a session, so OpenAPI/Swagger is told **for documentation only** via `require_session_docs` (`presentation/web/security.py`) — an `APIKeyCookie(auto_error=False)` security marker that renders the lock icon + "Authorize" without ever enforcing anything (the interactor stays the single source of truth). Attach it to protected routes alongside `AUTH_RESPONSES` (401/403, `presentation/web/responses.py`): set both on the `APIRouter(...)` constructor for fully-protected routers (they propagate to included sub-routers), or per-operation via `dependencies=[require_session_docs]` for routers that mix public and protected endpoints (e.g. `voting.py`). Public routes carry neither; `VALIDATION_RESPONSES` (422) is the only globally applied response set, and `FanfanAPI` (`presentation/web/openapi.py`, the app class at both build sites) prunes it from operations with no parameters and no body, which cannot fail validation.

### Route shape

- **No trailing slash.** A collection is `/users`, not `/users/` ([Zalando: normalized paths](https://opensource.zalando.com/restful-api-guidelines/)). A router's root route takes the empty path (`@router.get("")`), which FastAPI allows only under a non-empty prefix — so a package that assembles sub-routers (`routes/schedule/`, `routes/current_user/`) passes its prefix on each `include_router`, not on the parent router.
- **A DELETE carries no body.** Content in a DELETE has no defined semantics and some servers reject it ([RFC 9110 §9.3.5](https://www.rfc-editor.org/rfc/rfc9110#section-9.3.5)); identify the target in the path or the query (`DELETE /push?endpoint=…`).
- **A redirect route declares it.** Set `status_code` and `response_class=RedirectResponse` on the decorator, or FastAPI also documents a JSON 200 the route never sends (the OAuth start and callback routes).

## Persistence & Transaction Management

- **Driver**: psycopg 3 for the async engine and the outbox `LISTEN` connection alike ([ADR-0018](adr/0018-psycopg-3-as-the-postgres-driver.md)). `DatabaseConfig.build_connect_args()` (`adapters/db/config.py`) sends the safety timeouts as libpq `options` and pins the session `TimeZone` to UTC. A new entrypoint that calls `asyncio.run` must pass `loop_factory=loop_factory()` (`adapters/db/event_loop.py`): psycopg's async mode cannot run on Windows' default ProactorEventLoop.
- **ORM Models**: SQLAlchemy database models live strictly under `adapters/db/models/`. Columns are typed with **standard/SQLAlchemy storage types only** (`str`, `int`, `uuid.UUID`, `datetime`, …) plus `StrEnum`s mapped through `str_enum_column()` (`adapters/db/models/base.py`), which stores the enum **value** in a `VARCHAR` guarded by a CHECK constraint. There are deliberately **no native PostgreSQL `ENUM` types** — a CHECK is far cheaper to evolve than `ALTER TYPE ... ADD VALUE`. Do **not** annotate columns with domain value objects (e.g. `Mapped[UserId]`): keeping the ORM in storage types decouples it from `core/` and prevents a VO's underlying type from silently driving the column type (drift with no migration). The trade-off — VO ↔ storage conversion happening in one explicit place (the gateway's mapping functions) instead of implicitly — is intentional.
- **Shared base & mixins** (`models/base.py`, `models/mixins/`): `BaseORM` holds the shared `metadata` (with the `ix`/`uq`/`ck`/`fk`/`pk` naming convention that the constraint-violation handling relies on), the universal `created_at` audit column, and a generic `__repr__`. Compose the rest from mixins rather than re-declaring per model:
  - `UUIDPrimaryKeyMixin` (`models/mixins/pk.py`) — the time-ordered uuid7 `id`. On nearly every model; `AppSettingsORM` is the deliberate exception (singleton `int` PK).
  - `UpdatedAtMixin` (`models/mixins/timestamps.py`) — the `updated_at` column. **Opt-in**: mix it into a model only if the table actually receives UPDATEs. Append-only / audit tables (`votes`, `feedback`, `schedule_changes`, `user_flags`, `user_permissions`, `push_subscriptions`) omit it — an `updated_at` that can never move is just noise. (`created_at` stays everywhere; only `updated_at` is opt-in.)
  - `OrderMixin` (`models/mixins/order.py`) — the deferred-unique float `order` column plus its per-table sequence.
- **Table names are plural and fully spelled** (`users`, `tickets`, `schedule_changes`, `push_subscriptions`, …). `feedback` (uncountable), `schedule` (a collective noun: the whole programme, one entry per row) and `app_settings` (singleton) are the only non-plural names. Renaming a table means renaming its constraints/indexes/sequence too, so the naming-convention names stay in sync — see the `model convention cleanup` migration for the pattern.
- **Enum columns store the value, not the member name**: domain enums are `StrEnum`s (`core/vo/`), and every persisted enum column is declared with the `str_enum_column(EnumCls, name=..., length=...)` helper (`models/base.py`) rather than a hand-rolled `Enum(...)`. The helper fixes `native_enum=False`, `create_constraint=True`, and `values_callable=lambda e: [m.value for m in e]`: SQLAlchemy's default persists the member _name_ (`"VISITOR"`); `values_callable` flips it to the _value_ (`"visitor"`) so the DB matches what the API, DTOs and frontend already use. Pass `server_default` (and `default`) as the value too (`UserRole.VISITOR.value`). Keep this uniform — a column that stores names is drift, not a variant.
- **Every `relationship()` is declared `lazy="raise"`**: under `AsyncSession` an implicit lazy load is IO that cannot run outside `await` (it fails with `MissingGreenlet` at whatever line first touches the attribute), so touching an unloaded relationship raises instead. A query whose rows reach a mapping function that reads a relationship must eager-load it — `joinedload()` for many-to-one, `selectinload()` for collections — ([SQLAlchemy: preventing implicit IO](https://docs.sqlalchemy.org/21/orm/extensions/asyncio.html#preventing-implicit-io-when-using-asyncsession)). The flush is unaffected: raiseload does not apply inside the unit of work.
- **Complexity has a ceiling.** Ruff runs `ALL` plus preview rules opted in by code (`explicit-preview-rules`), listed and grouped in `backend/ruff.toml`. The ones that shape code most are `PLR6301` (a method that never uses `self`), `PLC2701` (private imports), `PLR1702` (nesting deeper than 3), `PLR0914` (too many locals) and `PLR0916` (too many boolean terms), plus the `FURB` and `RUF` rules that point to a simpler equivalent. Before opting a new preview rule in, run it against the codebase and leave it off if it only flags framework-required shapes. McCabe complexity is capped at 8. Dishka providers in `main/` and test doubles are exempt from `PLR6301`, because a framework fixes their shape. `ty` fails on warnings too (`error-on-warning`), so `unused-awaitable`, `deprecated` and `redundant-cast` block the gate. It also requires `@override` on every port implementation and rejects an `Any` leaking into a typed name (`unsound-assignment`). ORM models are exempt from that last rule, because `mapped_column()` returns an untyped descriptor.
- **Annotate every function — parameters and return.** `ty` skips an unannotated function entirely, checking neither its body nor inferring its return type, so every caller sees Unknown. Ruff's `ANN` group enforces this, and `ANN401` keeps an explicit `Any` costing a `noqa` that says why. A forwarding `*args`/`**kwargs` is the one exemption (`allow-star-arg-any`).
- **VO ↔ storage conversion happens only in the gateway's mapping functions**: the module-level `_to_model`/`_from_model`/`_parse_*_dto` functions atop each gateway module are the single seam where domain value objects are constructed from rows (`UserId(orm.id)`, `Email(orm.email)`) and unwrapped back (`model.id`, `model.email.value`). Because they must wrap every value, a VO whose base type drifts surfaces as a **type error right there** — caught by `just backend-typecheck`, not at runtime. (Storage-vs-actual-column drift is still Alembic's job.)
- **Gateways**: Concrete SQL queries, database reads, and inserts are isolated in gateway implementations under `adapters/db/gateways/` (one per aggregate/concern). Each implements its aggregate's abstract `gateways/` port (reads and writes). Order methods to mirror the port: aggregate persistence first (`add`/`get`/`save`/`delete`), then `read_*` DTO projections last under the same `# Read projections (return DTOs, not aggregates)` divider, so port and adapter read identically top-to-bottom.
- **Feed pagination is keyset, not offset** ([ADR-0023](adr/0023-keyset-cursor-pagination-for-feeds.md)): a list the client scrolls takes `CursorPagination` (`application/dto/page.py`) and sorts `(created_at DESC, id DESC)`. The gateway reads `pagination.fetch_limit` rows (one past the page) and filters with `rows_after(...)` (`adapters/db/pagination.py`) when `pagination.after` is set; the interactor splits them with `cut_page`, which returns the page and the opaque `next_cursor` token. The route takes the token through `PageCursorQuery` and decodes it with `CursorPagination.from_token`, which raises `InvalidPageCursor` (400) on a malformed one. The organizer users directory pages the same way, with its filters applied to both the page and its `total`. Reference sets bounded by the programme (voting nominations and participants) are not paged: the client searches them in memory ([ADR-0024](adr/0024-keyset-paging-for-the-users-directory.md)).
- **Constraint-violation handling**: A gateway must never leak a raw `IntegrityError` for a _known, reportable_ conflict — translate it to a domain exception at the boundary so inner layers stay pure. There are two sanctioned styles, chosen by whether the caller needs to hear about the conflict:
  - **Reportable conflict → `translate_integrity_error` (`adapters/db/constraints.py`)**. Force the write with `await session.flush()` _inside_ the `with` block so the violation surfaces at the gateway (not later at `uow.commit()`), and map the constraint name to a domain exception: `with translate_integrity_error({"uq_votes_user_id": VoteAlreadyExists}): ...`. It dispatches on the DB constraint name (robust, driver-tolerant — relies on the `uq_`/`fk_`/`ix_` naming convention), raises `from` the original, and **re-raises any unmapped constraint** so an unexpected `NOT NULL`/`CHECK` bug is never swallowed or mislabeled. This is the default — and it is also the race-safe backstop, so do **not** pre-`SELECT` to avoid the insert.
  - **Idempotent marker → `INSERT ... ON CONFLICT DO NOTHING`**. Only when a duplicate is a no-op the caller need not hear about (e.g. `user_flags`: a user either has a flag or not). Race-free at the DB level and avoids the try/except, but it signals "nothing happened" via `rowcount`, never an exception — so do not use it where a conflict must surface as a domain error.
- **Mapping functions**: ORM model ↔ domain entity translation lives in module-level `_`-prefixed functions (`_to_model`/`_from_model`/`_parse_*_dto`) at the top of each gateway module, above the class — the same shape and placement as the `_select_*_dto` query helpers. Gateways must map ORM rows to pure domain objects (and back) through these — never leak ORM models out of the adapter layer. Keep them **plain functions, not methods or a class**: they are pure transforms of their arguments with no gateway state, so a class or `@staticmethod` namespace would only add ceremony (this is a deliberate departure from the generic Data Mapper "separate class" advice — the seam that matters here is _separation from the query logic_, which colocated functions already give). When you add a new persisted aggregate, you add a model and a gateway (with its mapping functions) together. The only input a mapping function does not take from its argument is the adaptix `Retort` for JSONB (de)serialization (e.g. `app_settings`): the gateway receives the shared `Retort` from DI and passes it in as a parameter — do not instantiate `Retort()` ad-hoc (adaptix caches per-type morphers, so it is built once and reused).
- **Transaction Management (Unit of Work)**: Database commits and rollbacks in use cases are managed strictly by injecting `uow: UnitOfWork` (from `application/ports/uow.py`) and invoking `await self.uow.commit()`. Do not call raw SQLAlchemy session commits (`session.commit()`) inside interactors. The `UnitOfWork` also tracks aggregates and, on commit, writes their domain events, plus any `enqueue`d commands, to the transactional outbox in the same transaction (see [Domain Events](#domain-events)) — gateways call `self.uow.register(aggregate)` inside their `add`/`get` methods so the interactor never pulls or publishes those events by hand.
- **Migrations**: **Prefer autogenerated migrations over hand-written ones** — generate via `just backend-generate <name>` (against a running app DB) or `just backend-generate-auto <name>` (boots a throwaway prod-matching Postgres 18 via `backend/scripts/generate_migration.py`, using testcontainers — the same container mechanism as the drift test; use this where no DB is running, e.g. Claude Code on the web), then apply with `just backend-migrate`. **Always review the generated file before committing**: autogenerate emits column **renames** as drop+create (data loss) and can get **server-default** changes wrong, so hand-edit those cases. Autogenerate has `compare_type` on (Alembic's default since 1.12.0), so it detects column **type** drift between the ORM models and the database — which pairs with the mapping functions' compile-time VO checks to cover both seams. Note that Alembic does **not** diff CHECK constraint bodies, so adding or removing an **enum member** autogenerates an _empty_ migration — write the constraint swap by hand (`fanfan-migrations` skill; worked example in `2026_07_17_0800-a1b2c3d4e5f6_add_tickets_generate_permission.py`).

## Config vs settings

Two different things wear these two words, and the split is deliberate — keep it when you name a new value or decide where one lives.

- **Config** — _static, operator-owned, boot-time, read-only at runtime._ Read from `.env` into `EnvConfig` (`adapters/config/models.py`) and its per-domain slices (`WebConfig`, `NatsConfig`, `OutboxConfig`, `SchedulerConfig`, …). Holds secrets and infra endpoints plus deployment posture and static tuning. Changing one means editing `.env` and restarting the process; it never mutates while the app runs.
- **Settings** — _dynamic, user-owned, runtime-editable, persisted._ Stored in the database and changed through the UI by an authenticated user: the singleton `AppSettings` aggregate (`core/models/app_settings.py`, one row `id==1`) an organizer edits at `/settings`, and per-user `UserSettings`. A change takes effect immediately (and, for `AppSettings`, fans out over SSE) with no redeploy.

**Where does a new value go?** Ask who owns it and whether changing it needs a redeploy. A secret, an infra endpoint, or deployment posture → config. A product value a non-technical organizer flips during the event (e.g. `festival_start`, `voting_enabled`) → settings. The two must **not** be merged: config carries secrets that must never reach a DB row or a client, and settings must change without an ops action — the friction between them is the point.

Two naming edges are intentional, not drift:

- **`GET /config` / `PublicConfigDTO`** serve a _projection of settings_, yet keep the "config" name because it is right from the **consumer's** side: to the unauthenticated SPA it is read-only bootstrap data fetched before login and cached on a cold/offline load. Server-side it is still sourced from `AppSettings`.
- **`LimitsConfig`** is a static-shaped tuning bundle nested _inside_ `AppSettings`; it is organizer-editable like the rest of the aggregate. The public/private visibility line is drawn at the read projection (the `PublicConfigDTO` allowlist), never by table layout — a field's visibility can change without a migration.

## Dependency Injection (Dishka)

- **DI Container**: Wired in `main/di.py` using Dishka providers (defined under `main/ioc/`).
- **Config narrowing**: `EnvConfig` (`adapters/config/models.py`) is the single settings aggregate, but a factory should depend on the **narrowest slice it needs**, never the whole aggregate. The provider that _owns a domain_ unpacks that domain's slice from `EnvConfig` (e.g. `StreamProvider` → `NatsConfig`, `TelegramProvider` → `TelegramConfig`, `MailProvider` → `MailConfig | None`, `PushProvider` → `PushConfig`, `VkProvider` → `VkConfig`, `CaptchaProvider` → `AltchaConfig | None`, `InteractorsProvider` → `OutboxConfig`/`NotificationConfig`). Only genuinely cross-cutting leaves (`WebConfig`, `DebugConfig`, `timezone`) plus the `EnvConfig` root itself stay in `ConfigProvider` (`main/ioc/config.py`). Consuming the full `EnvConfig` is reserved for the composition roots (`parsers.get_config`, `main/worker.py`).
- **Serialization (adaptix `Retort`)**: The base `Retort` used to (de)serialize plain-dataclass models is built once in `adapters/serialization.py` (`create_retort`) and provided app-scoped by `SerializationProvider` (`main/ioc/serialization.py`). Inject `Retort` wherever you serialize (a gateway's JSONB mapping functions, receiving it as a parameter from the gateway; the NATS realtime gateway; vendor API clients). Dishka resolves by type, so a configuration that needs different rules gets its **own `NewType` alias** keyed separately — provide it under that alias and inject the alias, so it never collides with the base `Retort`.
- **Router/Presenter Injection**: Use the `@inject` decorator and `FromDishka[...]` type annotations to inject interactors into routes or presenters. Do not use standard FastAPI `Depends(...)` for dependencies managed by Dishka.
  ```python
  from dishka import FromDishka
  from dishka.integrations.fastapi import inject

  @router.get("/voting/status")
  @inject
  async def get_voting_status(
      interactor: FromDishka[GetVotingStatus]
  ) -> VotingStatusDTO:
      return await interactor()
  ```

## Domain Events

Two kinds of message share one transport, both subclassing `Message` (`core/events/base.py`) ([ADR-0040](adr/0040-commands-separate-from-domain-events.md)):

- **Domain event** (`DomainEvent`, `core/events/`) — a fact an aggregate records. Past tense; any number of subscribers may react, and the producer does not know them (`NotificationCreated` fans out to three channel consumers).
- **Command** (`Command`, `application/commands/`) — an instruction from a use case to do work later. Imperative; exactly one handler (`RunSyncCommand` → `run_requested_sync`). It lives in the application layer: asking for work is the use case's business, not the domain's.

Both reach NATS through the outbox, or through `EventBroker` (port: `application/ports/events_broker.py`) when a consumer publishes them, and are consumed by FastStream subscribers in `presentation/faststream/routes/`.

**Do not add a published message without a corresponding subscriber.**

### Naming standard

- **Event class** — PascalCase, **past tense**, `<Entity><PastVerb>` (e.g. `ScheduleChangeCreated`, `ScheduleChangeUndone`). An event records something that _already happened_; if you can't name it in the past tense it is probably a command.
- **Command class** — `<Imperative><Subject>Command` (e.g. `CreateNotificationCommand`, `CancelMailingCommand`). The suffix keeps it apart from the interactor that handles it (`CreateNotification`).
- **`subject` ClassVar** — the NATS/JetStream subject the message is published and subscribed on, and the wire contract. Lowercase, **dot-separated** hierarchy, snake_case within a segment, the verb as the final segment. Events: `<context>[.<entity>].<past-verb>` — `schedule.change.created`, `notifications.created`. Commands: `cmd.<context>[.<entity>].<imperative-verb>` — `cmd.notifications.create`, `cmd.sync.run`; the prefix keeps commands separable on the wire (a later work-queue stream could take `cmd.>`). The context segment names the bounded context (`notifications`, `schedule`, `sync`). Unlike SSE event names (single token, no dots — see [Realtime (SSE)](#realtime-sse)), dots here are intentional: JetStream consumers bind with hierarchical wildcards (`notifications.>`).
- **Stability** — a `subject` is a published contract. Renaming one orphans existing durable consumers and any outbox rows already written with the old subject, so treat changes as a migration, not a rename.

### Events raised by aggregates (preferred)

When an event directly records a state change on an aggregate, raise it inside the aggregate method using `record_event()`. The interactor does **not** publish these — the `UnitOfWork` handles them automatically. The gateway registers the aggregate when it is added or loaded, and `uow.commit()` writes the recorded events to the **transactional outbox** in the same transaction as the state change (see [Transactional outbox](#transactional-outbox)):

```python
# core/models/schedule_change.py
class ScheduleChange(AggregateRoot):
    @classmethod
    def moved(cls, *, event_id, ...) -> Self:
        instance = cls(...)
        instance.record_event(ScheduleChangeCreated(schedule_change_id=instance.id))
        return instance

    def mark_undone(self) -> None:
        self.record_event(ScheduleChangeUndone(mailing_id=self.mailing_id))

# adapters/db/gateways/schedule_changes.py — register on add/get
async def add(self, change: ScheduleChange) -> None:
    self.session.add(_from_model(change))
    await self.session.flush(...)
    self.uow.register(change)

# application/interactors/schedule_mgmt/… — no manual publish
change = ScheduleChange.moved(event_id=..., ...)
await self.changes_gateway.add(change)
await self.uow.commit()  # writes the change + a ScheduleChangeCreated outbox row atomically
```

`ScheduleChange` follows this pattern; every gateway registers its aggregate in each `add`/`get` method. The `UnitOfWork` pulls events from each registered aggregate exactly once (the internal event list is cleared on store) and writes them as outbox rows in the same transaction, so a rolled-back transaction never emits events. When you add a new aggregate that records events, register it in its gateway's `add`/`get` methods — that is the only wiring required.

### Transactional outbox

Aggregate events are **not** published to NATS on commit — that would be a dual write: if the process dies between the DB commit and the publish, state is persisted but the event is lost ([ADR-0004](adr/0004-transactional-outbox-for-domain-events.md)). Instead, `uow.commit()` serializes each recorded event into an `OutboxEventORM` row (`adapters/db/models/outbox.py`) committed in the **same transaction** as the aggregate change, and a relay delivers it asynchronously:

- **Relay** — `PublishOutboxEvents` (`application/interactors/outbox/`), driven by `OutboxRelay` (`presentation/faststream/outbox_relay.py`), a background task the worker starts after its broker and cancels on shutdown ([ADR-0046](adr/0046-nats-message-schedules-replace-apscheduler.md)). It reads unpublished rows `FOR UPDATE SKIP LOCKED` in creation order (`created_at` with the uuid7 `id` as tiebreaker — rows from one commit share the transaction timestamp), calls `EventBroker.publish_raw(subject, payload, message_id, occurred_at)`, marks them published, and commits. `occurred_at` is the row's commit time, sent as the `Occurred-At` header (read back with `presentation/faststream/headers.py:read_occurred_at`) so a consumer can tell how late an event arrives. `process_schedule_change` uses it: its notifications describe the schedule as it is _now_, so a change older than `SCHEDULE_NOTIFICATION_LIFETIME` (10 minutes, `core/vo/notification.py`) is dropped and its mailing marked failed rather than announcing the wrong event.
- **Failed publishes** — a row whose publish fails is held back, not retried at the head of the queue: the relay marks the already-acked prefix, bumps the row's `attempts`, stores a truncated `last_error`, sets `next_attempt_at` (doubling from 1 s, capped at 5 min, on the database clock), commits, and ends the drain. The fetch skips rows whose retry is not yet due, so the next wake delivers the rows behind it — one row NATS keeps rejecting cannot stall every event queued after it. Stopping at the first failure (rather than trying the rest of the batch) keeps a NATS outage to one timed-out publish per wake. Rows are **never** given up on: parking them after N attempts would strand every event queued during a long NATS outage. Instead each failure logs a WARNING, and the 10th logs once at ERROR (`relay_event=publish_stuck`), which Sentry captures. To inspect a stuck row, query `outbox_events WHERE published_at IS NULL AND attempts > 0`; to retry one immediately, set its `next_attempt_at` to `NULL`.
- **Wake-up** — the loop is _pushed_, not clock-driven: an `AFTER INSERT` trigger on `outbox_events` fires `pg_notify('outbox_new', …)`, and `PostgresOutboxSignal` (`adapters/db/outbox_signal.py`, port `application/ports/outbox_signal.py`) holds a dedicated psycopg `LISTEN` connection (autocommit, reading `notifies()` between `SELECT 1` probes every 30 s so a silently dropped socket is noticed, and reconnected with capped exponential backoff) that wakes the relay the instant an event is enqueued (near-instant delivery, not one poll-interval). `OutboxConfig.poll_interval_seconds` is only the **backstop**: the relay still drains at least that often so a missed notification (listener reconnecting, transport blip) costs latency, never a lost event — which is what keeps LISTEN/NOTIFY a pure speed layer over the durable poll rather than the delivery mechanism ([ADR-0015](adr/0015-listen-notify-wakes-the-outbox-relay.md)). The trigger is created in a hand-written migration (autogenerate neither emits nor diffs triggers), and its channel name is a contract with `OUTBOX_CHANNEL` in the adapter.
- **Delivery guarantee** — at-least-once: a row is marked published only after NATS acks it. Consumers stay idempotent; the row id is sent as `Nats-Msg-Id` so JetStream dedups redeliveries within its window. Delivery to _consumers_ is bounded by the JetStream stream retention (`presentation/faststream/jstream.py`, `max_age` 24h): once a row is marked published the outbox never resends it, so a consumer outage longer than the stream retention loses events.
- **Retention** — `PurgeOutboxEvents` drops delivered rows older than `OutboxConfig.retention_days`, on the `SCHEDULER__OUTBOX_RETENTION_CRON` cron (nightly by default).
- **Scope** — recorded events and `enqueue`d commands alike. Only a message a consumer publishes, which its own redelivery covers, goes direct (see [Commands](#commands)).

This makes domain-event delivery atomic with the write; latency is near-instant through the wake-up above, and at worst one backstop poll interval when a notification is missed. SSE/realtime is unaffected — it uses `RealtimeGateway`, not `EventBroker`.

### Commands

A command asks for work after the commit: create a notification, process a broadcast, run a sync, cancel a mailing. The interactor builds it and hands it to the unit of work, which writes it to the outbox in the same transaction as the state it depends on:

```python
# application/interactors/sync/request_sync.py
run = SyncRun.create(source=data.source, by_user_id=current_user.id)
await self.sync_run_gateway.add(run)
self.uow.enqueue(RunSyncCommand(sync_run_id=run.id, source=run.source))
await self.uow.commit()  # the run row and its command, atomically
```

`AwardQuestPoints`, `CancelQuestAward`, `SendBroadcast` and `CancelMailing` enqueue the same way. An aggregate that knows what its notification says builds it (`QuestAward.award_notification()`), and the interactor enqueues it — an aggregate never records an instruction as if it were a fact.

A consumer may publish a command directly through `EventBroker` instead: it is already redelivered on failure, so the message it was handling is its durability. The notification fan-outs (`ProcessBroadcast`, `SendScheduleChangeNotifications`) hand their recipients to `NotificationFanOut` (below), which publishes a `NotificationCreated` per stored notification, and `undo_schedule_change` reacts to `ScheduleChangeUndone` with a `CancelMailingCommand`. Inject `EventBroker` into an interactor only for that case — or for a request whose loss is harmless (`SendPersonalNotification`, `SendTestNotification`).

> Email login/confirmation codes are deliberately **not** commands. `request_login_code.py` and `change_email.py` send them synchronously by calling `SendLoginCodeEmail` / `SendEmailConfirmationCode` inside the request, so an SMTP failure reaches the caller instead of failing silently after the UI has already told the user the code was sent. The send runs inside the per-address cooldown claim, which a failed send gives back — the cooldown stays unspent, so the user can retry immediately.

> Keep domain events honest: a domain event must record an actual state change (past tense). Do **not** call `record_event()` for an action that mutates nothing, or to ask for work — that is a command.

`EventBroker.publish` goes through JetStream and waits for the PubAck, like the relay: a core NATS publish gets no reply, so an event the stream failed to store would vanish silently ([NATS: Publishing](https://docs.nats.io/learn/jetstream/publishing)). A failed publish raises inside the consumer that triggered it, which then redelivers. A message with a stable identity overrides `Message.dedup_id()` (`CreateNotificationCommand` returns its notification id, `NotificationCreated` the same id under its subject, since JetStream dedups ids stream-wide) so a rerun fan-out is deduplicated via `Nats-Msg-Id`. A fan-out goes through `EventBroker.publish_many`: it tries every event even when some fail — one rejected publish says nothing about the rest, so none is cancelled — keeps at most `_MAX_IN_FLIGHT_PUBLISHES` awaiting their ack (nats-py sets no limit of its own: [NATS: Advanced publishing](https://docs.nats.io/learn/jetstream/advanced-publishing)), then raises the failures together as an `ExceptionGroup` so the consumer redelivers and the rerun republishes only what did not land.

### Consumers: acks and redelivery

The outbox gets an event into JetStream at least once; the consumer must not throw that away. Three rules, enforced by `tests/unit/presentation/test_redelivery.py`:

- **Never the default ack policy.** FastStream's default for NATS is `REJECT_ON_ERROR`, which terminates the message on the first unhandled error — the event is gone. Use `NACK_ON_ERROR`, or `MANUAL` where the handler maps outcomes to ack decisions itself (`_deliver_to_channel`).
- **Bounded, delayed redelivery.** `RedeliveryMiddleware` (`presentation/faststream/redelivery.py`, a broker middleware) turns an unhandled error into a nak with a growing delay (1 s → 5 min) and terminates the message at `MAX_DELIVER` deliveries, logging `Message dropped after max deliveries` at ERROR. A plain nak redelivers immediately and JetStream's MaxDeliver defaults to unlimited, so without it a poison message loops hot forever ([NATS: Ack responses and redelivery](https://docs.nats.io/learn/jetstream/acknowledgment)). The delay rides on the nak rather than the consumer's `BackOff`, which NATS applies only to AckWait expiry and which replaces AckWait with its first step.
- **Declared config reaches the server.** Every durable is declared with `consumer_config()` (carrying `max_deliver`). nats-py sends a ConsumerConfig only when it _creates_ a durable, and the NATS volume outlives deploys, so `sync_consumer_configs` re-applies each declaration on startup (a same-name `add_consumer` updates editable fields in place) and logs `Consumer config updated` with the fields that changed. The update is applied unconditionally; the diff only feeds the log, because it compares just the fields a declaration sets and would miss, say, a removed `ack_wait` falling back to the server default. A change to a non-editable field logs a warning instead; recreate that durable by hand.

Redelivery makes every consumer run more than once for some messages, so handlers stay idempotent — deterministic ids, `ON CONFLICT DO NOTHING`, and state guards like `Mailing.ensure_active()` and `SyncRunTracker.start()` (which skips a settled run and resumes an interrupted one). A handler that can outlast AckWait wraps its work in `in_progress_heartbeat` (`run_requested_sync` and the two fan-out consumers, `process_schedule_change` and `create_new_broadcast`, do) so it is not redelivered needlessly while alive — but a lost beat can still let AckWait lapse, so redelivery never proves the previous worker stopped. Once a message is out of deliveries the middleware terms it and nothing runs it again, so the two fan-out consumers check `is_last_delivery` on failure and `abandon` their mailing (FAILED) before re-raising. Work that must not run twice takes a `WorkerLock` (`adapters/db/worker_lock.py`): a Postgres session-level advisory lock on a dedicated connection, released the moment the holder's connection closes. Sync worker locks are keyed per source, not per run (`sync_lock_key`). A redelivered sync trigger that cannot take its source's lock raises `SyncAlreadyRunning`, so the consumer backs off and retries until the live worker finishes or dies.

## Realtime (SSE)

Browser push goes over Server-Sent Events, separate from the domain-event/outbox path: the application layer (interactors and services, never a route or consumer) publishes an `SSEMessage` via `RealtimeGateway` after its commit (`adapters/nats/realtime_gateway.py`), which fans out over NATS subjects to every open `/events` stream (`presentation/web/routes/sse.py`). It carries no committed state, so it never touches the `UnitOfWork` or the outbox. The `sse.*` subjects are core NATS only: the JetStream stream does not capture them, because nothing replays a live update.

An SSE message to every open screen is a **live update**, never a "broadcast": that word is the organizer's hand-written mailing ([GLOSSARY.md](../GLOSSARY.md)). The `sse.broadcast.*` NATS subject keeps its name because it is wire-internal and renaming it buys nothing a reader sees.

**Every SSE event name is a member of the `SSEEventName` `StrEnum`** (`application/dto/realtime.py`) — never a bare string literal. `SSEMessage.event_name` is typed to the enum, so a typo is a type error, not a silently dead event. To add an event: add a member here, then mirror it in the frontend `SSEEventMap` (`frontend/src/lib/services/events.svelte.ts`).

Naming standard for new events:

- **snake_case, single token — no dots.** The subject is built as `sse.broadcast.{event_name}` / `sse.user.{user_id}.{event_name}` and consumers subscribe with a single-token wildcard (`sse.broadcast.*`). A dot in the name splits into extra subject tokens and silently stops matching the wildcard. (`SSEEventName` being a `StrEnum` means it interpolates straight into the subject and into the SSE `event:` field as its value.)
- Prefer `<entity>_<event>` for new names.
- The backend enum and frontend `SSEEventMap` are kept in sync **by hand** — SSE events are not part of the OpenAPI spec, so `just frontend-generate-api` does not cover them. Every enum value must have a matching `SSEEventMap` key.

**Liveness heartbeat**: the `/events` route injects a named `ping` event after `HEARTBEAT_INTERVAL_SECONDS` (15s) of stream silence — `ping` is the one `SSEEventName` never published via `RealtimeGateway`. Comment-based keepalives are invisible to the browser `EventSource` API, so the frontend watchdog (`HEARTBEAT_TIMEOUT_MS`, 3x the interval = 45s, in `events.svelte.ts`) relies on these pings to detect silently dead connections (Wi-Fi roaming, NAT timeouts) and reconnect. 15s sits inside the 30s floor of cellular NAT gateway idle timeouts. If you change the interval, keep it below common proxy idle timeouts (60s) and update the frontend timeout to match.

**Shutdown**: streams never end on their own, so uvicorn's graceful shutdown is bounded (`UVICORN_TIMEOUT_GRACEFUL_SHUTDOWN`, 5s). When it expires, uvicorn cancels the open streams and runs the lifespan shutdown. See [deployment.md](deployment.md#stopping-the-api-with-sse-streams-open).

## Notification Delivery

A notification travels fan-out → store → channels, and every hop is built to keep a schedule change's last recipient within seconds of its first ([ADR-0041](adr/0041-notification-fan-out-stores-in-chunks.md)).

- **Store in chunks.** `NotificationFanOut` (`application/services/notification_fan_out.py`) takes one mailing's notifications (or a mailing-less batch) and stores them 500 per transaction: lock the mailing row, `ensure_active`, one `INSERT … ON CONFLICT DO NOTHING RETURNING id` (`NotificationGateway.add_many`), commit. Given `mailing_id`, it marks the mailing FINISHED in the last chunk's transaction, or on its own when there is nothing to store ([ADR-0042](adr/0042-mailing-finishes-with-its-last-chunk.md)). Then it sends that chunk's live toasts and publishes its `NotificationCreated` events, so the channels start on the first chunk while later ones are stored. A cancellation is seen at the next chunk and raises `MailingAlreadyCancelled`; the fan-outs catch it and stop. `CreateNotification` (the `CreateNotificationCommand` handler) is a fan-out of one.
- **Send in parallel.** The three channel consumers (`presentation/faststream/routes/notifications.py`) run several handlers each (`max_workers`, FastStream's `ConcurrentPullStreamSubscriber`) and pull several messages per request. Telegram and VK are paced by a per-process `RateLimiter` (`adapters/rate_limiter.py`) under each provider's published quota; push has none to respect. The limiter is per process, so a second faststream container would double the rate.
- **Hold nothing across a send.** `SendNotification` reads the notification and mailing without row locks (`get(..., lock=False)`), and every notifier commits its own lookups before the external call, so a sender holds a pooled connection only for milliseconds and the workers can outnumber the faststream DB pool.
- **Order is rebuilt where it matters.** Parallel handlers do not keep delivery order, and a retry arrives after newer messages ([NATS: acknowledgment](https://docs.nats.io/learn/jetstream/acknowledgment)). So the order a fan-out builds is the order it _stores_ in: `SendScheduleChangeNotifications` puts subscription notices first, then the stage announcement (every user is opted in by default, so it is the big one), then the few editors. On the send side, `SendNotification` drops a stage notice (`NotificationType.is_replaced_by_later`: the announcement and editors' notice, not a subscription notice, which is about one act) that `NotificationGateway.is_superseded` reports a later mailing has already overtaken (`NotificationSuperseded`), so a late older one never ends up on top. Push lanes follow the same split: `schedule` for announcements and editor notices, `subscription` for a reader's own acts, so one never replaces the other on the shade.
- **Shutdown waits for sends.** The broker's `graceful_timeout` (15 s, `presentation/faststream/broker.py`) lets in-flight handlers finish on SIGTERM, and the worker service's `stop_grace_period` (20 s) stays above it. A message fetched but not started is never acked and waits out its AckWait, which is why each pull fetches only 8.
- **Urgency comes from the type.** `NotificationType.is_time_sensitive` (`core/vo/notification.py`) marks what a reader needs now: schedule changes, broadcasts and personal messages. Push sends those with `Urgency: high`, RFC 8030 §5.3's level for a "time-sensitive alert", which the push service delivers even to a phone saving battery; the rest go at `normal`. It is derived rather than stored because every notification of a type shares it. A per-broadcast "urgent" switch for organizers would make it a column.
- **Schedule notifications expire.** Their text describes the stage at the moment it was built, so one older than `SCHEDULE_NOTIFICATION_LIFETIME` is wrong, not late: `Notification.is_stale` makes `SendNotification` raise `NotificationExpired`, which the consumer rejects. Push additionally sends them with a TTL of what is left of that lifetime (`Notification.remaining_lifetime`) and a `Topic` so a newer one replaces one still waiting for an offline device ([RFC 8030](https://www.rfc-editor.org/rfc/rfc8030)). The `webpush` library sets only TTL, so `WebPushClient.send` adds the other two headers.

## Notification Formatting

A notification `body` is stored as a **small, safe HTML subset** so the same text can be highlighted across every delivery channel. The subset is the intersection of what Telegram's HTML parse mode accepts and what the web UI can render: `b`, `strong`, `i`, `em`, `u`, `s`, `a[href]`, `code`, `pre`, `blockquote`. Line breaks are stored as plain `\n` (no `<br>`/`<p>`), which Telegram treats as newlines and the web renders via CSS `white-space: pre-line`.

- **Single sanitization chokepoint**: every notification — broadcast, personal message, schedule-change template — is built into the persisted model in `NotificationFanOut._to_model` (`application/services/notification_fan_out.py`), which runs the body through the `HtmlSanitizer` port (`application/ports/html_sanitizer.py`, nh3 adapter `adapters/html/sanitizer.py`). `SendNotification` and the realtime SSE DTO both re-read the **persisted, already-sanitized** record, so sanitizing once covers web, Telegram, push, and VK. Never sanitize per-channel.
- **Per-channel rendering**: the web UI renders the stored body with `{@html}` (it is pre-sanitized — see [frontend.md](frontend.md)); the Telegram notifier (`adapters/tgbot/notifier.py`) sends it with `parse_mode=ParseMode.HTML` and only HTML-escapes the plain-text `title`; the push notifier (`adapters/push/push.py`) and the VK group notifier (`adapters/vk/notifier.py`) both strip all tags to plain text (and then `html.unescape` the result — nh3 leaves entities encoded, so a body like `5 &lt; 10 &amp; up` would otherwise reach the user with the entities literal) because OS notifications and VK messages do not render HTML. The VK notifier then deletes the group's own copy of each delivered message (`messages.delete` with `delete_for_all=0`, which removes it only on the group's side and keeps it in the user's inbox) so notifications don't pile up in the community conversation list organizers see; this cleanup is best-effort — the message is already delivered, so a failed delete is logged, never retried (retrying would redeliver a duplicate).
- **Shared HTTP client for the delivery notifiers**: the push and VK notifiers are request-scoped (they depend on request-scoped gateways/uow), but their outbound HTTP goes through an **APP-scoped, reused** `httpx2.AsyncClient` wrapped in a dedicated client type — `WebPushClient` (`adapters/push/client.py`) and `VkApiClient` (`adapters/vk/client.py`), each built once in its DI provider (`main/ioc/push.py`, `main/ioc/vk.py`). Reusing one client keeps the connection pool warm across a notification burst instead of re-handshaking per message ([httpx guidance](https://www.python-httpx.org/advanced/clients/)); wrapping it in a distinct type keeps a bare `httpx2.AsyncClient` out of the container, where it would be an ambiguous, collision-prone DI key. The notifier keeps only the delivery concern — rendering, resolving the user's address, and translating the vendor's failures into the `Notifier` port's three exceptions: `UserNotReachable` (this user can't be reached — unlinked or the provider refused: VK 7/15/901/902, Telegram forbidden/bad-request), `NotificationRetryAfter` (transient — VK flood 6/9, push 429/5xx, Telegram's own retry hint), and `NotificationChannelUnavailable` (channel-wide misconfiguration no retry can fix — a bad VK/Telegram token or missing/invalid VAPID keys, i.e. push 400/401/403). Push additionally prunes a retired subscription on 404/410. Whether the user _wants_ a given channel is application policy, not a delivery concern, so `SendNotification` (`application/interactors/notifications/send_notification.py`) checks `receive_telegram_notifications` / `receive_vk_notifications` and raises `UserNotReachable` before calling the adapter — push has no such toggle, since a live subscription is itself the opt-in. Adapters subclass their **specific** port (`TelegramNotifier(TelegramNotifierPort)`, etc.) per ADR-0005, so `ty` catches signature drift against the exact DI key. The FastStream consumers map those to JetStream ack decisions uniformly for every channel via the shared `_deliver_to_channel` helper (`presentation/faststream/routes/notifications.py`): retry → `nack(delay)`, unreachable/cancelled/channel-unavailable → `reject` (drop), success → `ack`. This mirrors the vendor-client split below (`BaseApiClient`), minus the adaptix DTO loading these two don't need.
- **Templates**: Jinja notification templates (`adapters/jinja/templates/`) may use the subset tags directly (e.g. `<b>`) to highlight key details. `autoescape=True` keeps `{{ variables }}` escaped, and the central sanitizer is the final safety net, so template-interpolated DB values can never inject markup. Sentences shown to users live in these templates, not as f-strings in interactors, so backend copy sits in one folder. A plain-text template (`*.txt.jinja2`: email alternatives, the schedule-change reason stored as the mailing summary) wraps itself in `{% autoescape false %}`, and an HTML template that embeds its output escapes it there. Count-dependent words use the `plural` filter: `{{ n }} {{ n|plural('минуту', 'минуты', 'минут') }}`.
- **Deep-link path**: each notification carries an optional in-app `path` (e.g. `/schedule`), set by the interactor that builds the `NewNotification` (the originating use case knows the target — `PushNotifier` cannot infer it from title/body). It is persisted on `Notification` and flows through both DTOs. The push notifier sends it as the absolute `notification.navigate` URL (built with `WebConfig.build_url`, as the VK notifier does), which the browser or the service worker (`frontend/src/service-worker/index.ts`) opens on click; the web UI makes notification list items and push toasts link to it. `None` falls back to the app root (`/`).
- **Push payload is a Declarative Web Push message** (`MessageData` in `adapters/push/client.py`): `web_push: 8030`, a `notification` dict (`title`, `body`, `navigate`, `tag`, `renotify`, `data.test`) and `mutable: true`. Safari 18.4+ Home Screen apps parse it and show the notification themselves; other browsers hand the same JSON to the service worker's `push` handler. The reason is WebKit's silent-push rule: an imperative handler that skips a notification gets its subscription revoked, and ours skips one while the app is visible. A declarative message carries no such penalty ([WebKit](https://webkit.org/blog/16535/meet-declarative-web-push/), [W3C Push API](https://w3c.github.io/push-api/)). `mutable` keeps the worker's handler running there so it can flag the app-icon badge.
- **Retention**: `PurgeNotifications` (`application/interactors/notifications/`) drops notifications older than `NotificationConfig.retention_days` (default 30), on the `SCHEDULER__NOTIFICATION_RETENTION_CRON` cron (nightly by default). In-app notifications lose relevance shortly after the convention, so the window is bounded to cap per-user growth; mirrors the outbox retention job.

## Profanity Filtering

User-chosen **public** text is screened for profanity behind the `ProfanityFilter` port (`application/ports/profanity_filter.py`, word-list adapter `adapters/profanity/filter.py`). Currently only the username is filtered: `UpdateCurrentUser._update_username` calls `contains_profanity` and raises `UsernameProfanity` (HTTP 400, code `USERNAME_PROFANITY`) before persisting. Feedback text is **intentionally not** filtered — it is private (organizer-only), so users may vent freely.

The adapter normalizes input before matching (casefold, fold Latin/leet look-alikes to Cyrillic, strip non-letters, collapse repeats), so obfuscated forms (`х.у.й`, `пизд@`, `хуууй`) are still caught. It combines two static word lists under `adapters/profanity/data/`: the vendored CC-BY [LDNOOBW](https://github.com/LDNOOBW/List-of-Dirty-Naughty-Obscene-and-Otherwise-Bad-Words) ru/en lists (used for **exact** normalized-token matches, see `NOTICE`) plus a curated `roots_ru.txt` of unambiguous mat stems (used for **substring** matches to catch inflections). To filter another field, inject the port and call it in that interactor.

## Rate Limiting

Two distinct rate-limiting ports exist — pick by semantics, do not overload one for the other:

- **`Cooldown`** (`application/ports/cooldown.py`): `async with cooldown.claim(key, seconds)` admits one caller per window and spends the window **only on a successful run**. Use it for "one _successful_ action per N seconds" flows where a failure should be retryable immediately (e.g. requesting/sending an email code). A concurrent caller fails fast with `CooldownActive` instead of queueing, and a block that raises gives the claim back. The Postgres adapter is one `cooldowns` row whose `expires_at` ends the wait. The claim is an upsert that takes over a row only once its window has passed, and the give-back deletes the row only while it still holds the caller's token, so it never removes a newer caller's claim.
- **Cooldown or advisory lock.** Pick by what a double run costs, following Kleppmann's efficiency/correctness split ([How to do distributed locking](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)). `Cooldown` is an _efficiency_ guard: a window that can expire under a slow holder, so on rare occasions two callers both run. That is acceptable for a cooldown and wrong for anything that corrupts data when run twice. For those, use `WorkerLock` (`application/ports/worker_lock.py`, Postgres session advisory lock): no TTL, held exactly as long as the holder's connection lives, and next to the rows it protects. It is deliberately not called a lease: a lease is a lock with a timeout (Kleppmann, after Gray & Cheriton), and this one never expires under a slow holder. Redis's own docs say the same: for correctness, add fencing and "don't assume that a lock is retained as long as the process that had acquired it is alive" ([Redis: Distributed locks](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)). Don't take a `WorkerLock` through a transaction-mode pooler (session locks need a stable session), and keep its connection out of any open transaction (`idle_in_transaction_session_timeout` would drop it). When the critical section is one transaction on the unit of work's session, a transaction-level advisory lock is simpler still: commit or rollback releases it, so it cannot leak through the pool. Schedule edits use one (`ScheduleEventGateway.lock_for_edit`) — `ScheduleEditService` takes it for every interactor that writes schedule events, because row locks cannot stop two edits computing the same `order` between the same neighbours. The announcement cooldown on move/skip/set-current lives under that same lock rather than in `Cooldown` (`ScheduleEditService`, `application/services/schedule_edit.py`): it compares the newest `schedule_changes.created_at` with the database clock, so it commits atomically with the edit and a failed edit never spends it. Undo deletes its change row, so an undone announcement stops counting towards the cooldown. A Postgres advisory lock carries no timestamp of its own, so a cooldown there always needs a row to measure from ([PostgreSQL: Advisory locks](https://www.postgresql.org/docs/current/explicit-locking.html#ADVISORY-LOCKS)). `Cooldown` serves the per-address email-code cooldown: its rows expire on their own, and the SMTP send it guards must not sit inside an open database transaction.
- **`RateLimiter`** (`application/ports/rate_limiter.py`): a fixed-window attempt **counter** that locks a key once a number of attempts is exceeded, regardless of success. Use it to penalize failures — password login brute-force, OTP guessing. Call `hit(key, limit=, window_seconds=)` on each attempt and `reset(key)` after success. It raises `TooManyAttempts`; callers catch and re-raise a flow-specific subclass (`TooManyLoginAttempts`, `TooManyOtpAttempts`) so each feature keeps its own error code/copy.

The adapters live in `adapters/db/expiring/` with the session store and the email-code registry ([ADR-0047](adr/0047-postgres-replaces-redis.md)). Each call runs in its own short transaction from `ExpiringSessionFactory`, a small pool of its own so a request holding its unit-of-work connection never waits on the same pool twice (bound to the test's connection in tests), outside the unit of work, so a rate-limit hit sticks when the caller then raises and rolls back. Rows past `expires_at` are ignored on read, so expiry never depends on cleanup; `PurgeExpiredState` deletes them nightly on the `SCHEDULER__EXPIRED_STATE_RETENTION_CRON` cron. `auth_sessions.user_id` references `users` with `ON DELETE CASCADE`. `SqlUserGateway` locks user rows `FOR NO KEY UPDATE`, not `FOR UPDATE`: a login holds the row while it creates the session on the separate pool, and `FOR UPDATE` would block that foreign-key check ([PostgreSQL: Row-level locks](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS)). `test_expiring_state_isolation.py` guards it. The login interactor passes the client IP in via its input DTO (filled by the web route through `presentation/web/utils.get_client_ip`) so the application layer never touches `Request`.

## Quest

Quest points live in an append-only ledger, `quest_awards` ([ADR-0035](adr/0035-quest-points-as-an-award-ledger.md)): a balance is the sum of a player's awards that are not cancelled, and the leaderboard ranks those sums with `row_number()`, ties going to whoever reached the score first. `QuestAward` (`core/models/quest_award.py`) owns the rules — no self-award, the per-award cap, and `cancel_refusal`, which both the cancel and the award list's `can_cancel` flag read so the button never offers what the server refuses. Awards take a client-generated UUIDv7 ([ADR-0034](adr/0034-client-generated-ids-for-unkeyed-creates.md)). Each award and cancellation enqueues a `CreateNotificationCommand` built by the aggregate, so the player's notification rides the outbox in the same transaction; the `quest` notification type is also the frontend's signal to refetch `GET /quest` and `GET /quest/history`, the player's own awards (cancelled ones included, without who gave them). The switch, cap and cancel window are `AppSettings.quest`; every quest endpoint raises `QuestDisabled` while it is off, and `GET /config` carries `quest_enabled` and `quest_max_award` for the UI. `quest:award` gives points and finds players by username prefix or user number (names and points only, not the directory's email or ticket); `quest:manage` sees and cancels every award. A player is named by their **user number** wherever a code is involved: the badge's QR carries it, the post-scan lookup takes it, and an award targets it, so an award queued offline from a scan needs nothing the code lacks. The number is a random six-digit `int` drawn in `core/vo/user.py`; `SqlUserGateway.add` redraws it inside a SAVEPOINT when it lands on a taken one (`uq_users_number`).

## Captcha

The unauthenticated `request-login-code` flow is guarded by a self-hosted [ALTCHA](https://altcha.org/) proof-of-work captcha behind the `CaptchaVerifier` port (`application/ports/captcha.py`), plus a per-IP limit. The port does both halves: `issue_challenge()` backs `GET /auth/captcha-challenge`, and `verify(token)` runs in `RequestLoginCode`; a missing, invalid, expired or replayed token raises `CaptchaVerificationFailed` (HTTP 403). The token and the client IP ride in on the input DTO so the application layer never touches `Request`; the route takes its own body model (`RequestLoginCodeBody`) so a client cannot supply the IP.

The interactor checks, in order: the per-IP cap (`LOGIN_CODE_IP_MAX_REQUESTS` per `LOGIN_CODE_IP_WINDOW_SECONDS` on the `RateLimiter` port, raising `TooManyLoginCodeRequests`, HTTP 429), then the captcha, then the per-email cooldown. The IP cap comes first so a source sending bad or replayed tokens burns its own budget too. It is generous because venue Wi-Fi and carrier-grade NAT share one address among many attendees. `GetCaptchaChallenge` has its own looser per-IP cap (`CAPTCHA_CHALLENGE_IP_MAX_REQUESTS`, same `TooManyLoginCodeRequests` code), since ALTCHA asks custom integrations to rate-limit challenge generation too, and the route caps `captcha_token` at 4 KB so a hostile payload never reaches the parser.

The feature is **optional and config-gated**: with no `ALTCHA__HMAC_KEY` (`altcha` unset in `EnvConfig`), `CaptchaProvider` (`main/ioc/captcha.py`) wires a `NoOpCaptchaVerifier` that issues `null` challenges and accepts everything, and the frontend then sends no token. With the key, it wires `AltchaCaptchaVerifier` (`adapters/captcha/altcha.py`): challenges use ALTCHA's deterministic mode (a random counter in `CHALLENGE_COUNTER_MIN`–`CHALLENGE_COUNTER_MAX`, pre-solved on the server, so every client does the same work), are HMAC-signed and expire after 10 minutes; verification is a local HMAC of the submitted key (no outbound call, so nothing to fail open), and each spent challenge signature is held as a `Cooldown` claim until its expiry, since a valid solution would otherwise replay. The challenge and derived-key signatures use two subkeys derived from the one configured key. Difficulty is the counter range plus `CHALLENGE_COST`. `just bootstrap` generates the key. See [ADR-0037](adr/0037-self-hosted-altcha-over-yandex-smartcaptcha.md).

## Anti-corruption layers (vendor sync)

The third-party sync flows for **cosplay2** and **TicketsCloud** are anti-corruption layers (ACLs): their whole job is to translate a vendor's wire format into our domain model. They sit **behind driven ports** (`application/ports/sources/`), so the `application/` layer depends only on those ports — never on `adapters/`. There are **no** `application → adapters` exceptions in the import-linter contract.

- **Source ports** (`application/ports/sources/`): `CosplaySource` and `TicketsSource` are `Protocol`s whose methods return **neutral application DTOs** (`ExternalNomination`, `ExternalParticipant`, `ExternalTicket`) — never vendor DTOs. The neutral DTOs use a vendor-agnostic `external_id` for the source's id; the interactor maps it onto the domain model's existing `cosplay2_id` / `ticketscloud_ticket_id` field. TicketsCloud sells a refunded ticket id again under a new order, so an imported ticket is keyed by the sale — `ExternalTicket.order_id` plus `external_id`, stored as `ticketscloud_order_id` / `ticketscloud_ticket_id` — and each sync revokes the sales named by approved refund requests (`TicketsSource.fetch_revoked_tickets`). A revoked ticket (`Ticket.revoked_at`) can no longer be linked; a user who linked it before the refund keeps it.
- **Source adapters** (`adapters/api/<vendor>/source.py`): `Cosplay2Source` / `TCloudSource` implement the ports. This is where the actual translation lives — grouping/renaming vendor fields and deciding which vendor records the domain recognizes (e.g. only `APPROVED` requests with a voting title become participants; only `DONE` orders with a barcode become tickets). Which role a TicketsCloud event's tickets grant is not vendor translation but organizer data: `ExternalTicket` carries the raw `event_id`, and `SyncTickets` / `ProcessTicketOrder` resolve it through `AppSettings.tickets` (edited from **Инструменты → Билеты**, under `tickets:manage`; an unmapped event grants `visitor`). Because the boundary speaks the domain's language, the interactors that consume them are named for the capability, not the vendor — `interactors/cosplay/sync_cosplay.py` (`SyncCosplay`), `interactors/tickets/sync_tickets.py` (`SyncTickets`), `interactors/tickets/process_ticket_order.py` (`ProcessTicketOrder`) — and together with the `TicketImportService` (`services/tickets_import.py`) they stay vendor-free and unit-testable with a fake source. The vendor name lives only where the vendor actually is: the `adapters/api/<vendor>/` packages, the `main/ioc/<vendor>.py` wiring, and the operator-facing knobs (CLI `sync tcloud` / `cosplay2`, the `SCHEDULER__SYNC_*_CRON` env keys, the `/webhooks/tcloud` URL).
- **Vendor clients** (`adapters/api/<vendor>/client.py`) are thin subclasses of `BaseApiClient` (`adapters/api/base.py`): a small `httpx2.AsyncClient` wrapper whose `_get` loads JSON responses into the plain-dataclass vendor DTOs via the injected adaptix `Retort`. Each endpoint is one explicit async method with a real return type — no decorator magic. httpx2 raises `httpx2.HTTPStatusError` on non-2xx (status at `error.response.status_code`); translate vendor errors here (e.g. 404 → `None` in `TCloudClient.get_order`). The client is a private detail of its source adapter. The base URL and auth headers are configured on the `httpx2.AsyncClient` in the DI provider (`main/ioc/<vendor>.py`), which also binds the source to its port. The client is provided at **APP scope** so one connection pool is reused across a paginated sweep and successive runs (the request-scoped source depends on it) — the same reuse pattern the delivery notifiers use (see "Notification Formatting"), and the app-wide convention: every `httpx2.AsyncClient` lives at APP scope, wrapped in a dedicated type, never a bare container dependency.
- **Aggregates are never built by the source.** A source returns _what the vendor asserts_; the interactor reconstitutes/merges the aggregate it owns — assigning identity and preserving domain-only fields the vendor doesn't know (`Nomination.is_votable`, the resolved `Participant.nomination_id`). That is why the ports return DTOs, not `Nomination`/`Participant`/`Ticket`.
- **Every sync run is recorded, whatever triggered it.** The three triggers — the organizer button (`POST /sync/{source}`), the `SCHEDULER__SYNC_*_CRON` jobs, and `cli sync tcloud` / `cosplay2` — all go through `ExecuteCosplaySync` / `ExecuteTicketsSync` (`interactors/sync/`), which wrap the bare `SyncCosplay` / `SyncTickets` with a `SyncRun` row via `SyncRunTracker` (`services/sync_run_tracker.py`). **Calling `SyncCosplay` / `SyncTickets` directly bypasses the audit row and the concurrency guard** — new callers must not. Manual runs go the long way round on purpose: `RequestSync` only writes a `PENDING` row plus an enqueued `RunSyncCommand` and returns 202, because the API container is replaced on every deploy and a full TicketsCloud sweep is unbounded; the durable NATS consumer (`presentation/faststream/routes/sync.py`) does the work in the worker. There are two `Execute*Sync` interactors rather than one dispatching on source because Dishka resolves constructor dependencies eagerly and each vendor's config provider raises when unset — one interactor asking for both would break single-vendor deployments.
- **Concurrency guard**: `uq_sync_runs_active`, a partial unique index on `sync_runs (source) WHERE finished_at IS NULL`, allows one active run per source. It stops a manual sync overlapping a scheduled one and doubles as the "is a run active?" signal the UI uses to disable the button. Collisions surface differently by trigger: `RequestSync` raises `SyncAlreadyRunning` → 409 for the organizer, while the cron/CLI path logs and skips (raising would put Sentry noise on every overlap). A worker killed mid-run would wedge the index forever, so `SyncRunTracker.reap_stale` fails runs older than `STALE_RUN_TIMEOUT` before starting a new one — but only while holding the source's `WorkerLock`. Every trigger path holds that lock for the whole run, so a slow sweep that is still alive is never reaped however long it takes. Vendor failures are recorded on the run and logged, never re-raised — re-raising would make the consumer redeliver and retry forever against a vendor that is simply down.
- If you build a new vendor integration, follow this shape: a thin client, a `*Source` adapter implementing a new port under `application/ports/sources/`, returning neutral DTOs. Do **not** inject a vendor client into the application layer, and do **not** dress a port up with methods that still traffic in vendor DTOs — that hides the coupling without removing it. **Any `application → adapters` import is a bug** and will fail `just backend-import-lint`.

## FestEngine webhook

The stage console, [FestEngine](https://github.com/DanteBC/FestEngine), posts what the operator does to `POST /api/webhooks/festengine` ([ADR-0048](adr/0048-festengine-drives-the-stage-over-standard-webhooks.md)). Set `FESTENGINE__WEBHOOK_SECRET` (`whsec_<base64>`, generated by FestEngine's **Generate** button) to enable it; unset, the route answers 404.

- **Checks, in order** (`routes/webhooks.py`): no secret, a bad [Standard Webhooks](https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md) signature, or a `webhook-timestamp` more than 5 minutes off answers 404 (`presentation/web/festengine/signature.py`). Then the raw body is parsed (`festengine/events.py`); a `row.show` / `row.play` older than 60 seconds answers `{"status": "stale"}`.
- **Event mapping** (`to_action_input`). The number is the leading digits of `data.row.num` (`"007"` → 7); dup rows already carry their source's number.

  | Event                                                | Action                                       |
  | ---------------------------------------------------- | -------------------------------------------- |
  | `row.show`, `row.play` (`row_type` `track` or `dup`) | Set the act current                          |
  | `row.skip` / `row.unskip`                            | Skip / unskip it                             |
  | `row.move`                                           | Move it after the event numbered `after_num` |
  | `row.unmove`                                         | Move it back, see below                      |
  | anything else, `row.updated` included                | `{"status": "ignored"}`                      |

- **Applying** (`ApplyStageConsoleAction`): acts as the system user, which needs `schedule:manage` (migration `4b8e2d6f1a37`). It takes the edit lock, resolves numbers, and runs the same `ScheduleOperations` as the organizer interactors. An edit that is already applied answers `unchanged` without spending the cooldown; otherwise `updated`. An unknown number is `404 EVENT_NOT_FOUND`, a broken rule the usual 400, the cooldown a 429 with `Retry-After`, which FestEngine honours.
- **Unmove** moves the act back after the entry its latest change recorded, only while that change is the system user's `MOVED` and the act still sits right after `after_num`. Anything else (an organizer moved it since, a retry already moved it back) is logged and ignored.

## Presentation Layers

- **HTTP APIs (`presentation/web/`)**: FastAPI routes mapping HTTP requests.
  - **Middleware is pure ASGI** (`presentation/web/middlewares.py`, registered with `app.add_middleware` in `factory.py`; the last one added runs outermost). Don't use `@app.middleware("http")` (`BaseHTTPMiddleware`): it wraps every request, SSE streams included, in an extra task and memory streams, and it stops contextvars propagating ([Starlette: Middleware](https://starlette.dev/middleware/)). To change response headers, wrap `send` and edit `MutableHeaders(scope=message)` on `http.response.start`.
- **Event Streaming (`presentation/faststream/`)**: FastStream handlers consuming NATS subjects. Inject interactors exactly the same way using `@inject` and `FromDishka`.
  - **Connections never give up.** Every NATS client (the consumer's broker, the DI-provided publisher broker, the realtime client) connects with `MAX_RECONNECT_ATTEMPTS` (`adapters/nats/config.py`, `-1`): nats-py's default closes the connection for good after about two minutes of retries, which would leave the process running but cut off ([NATS: reconnect attempts](https://docs.nats.io/using-nats/developer/connecting/reconnect/max)). Each connection is named (`fanfan-consumer`, `fanfan-publisher`, `fanfan-realtime`) so `/connz` tells them apart. The DI-provided ones drain when their container closes, which for the api is its FastAPI lifespan.
  - **Health.** The worker is an `AsgiFastStream` that serves `HEALTH_CHECK_PATH` through `make_ping_asgi`: 204 while the broker is connected, 500 while it is not. The image's `HEALTHCHECK` probes it the same way it probes the api ([FastStream: Healthchecks](https://faststream.ag2.ai/0.7/getting-started/observability/healthcheks/)).
- **Telegram — no interactive bot.** There is no long-polling bot service. Telegram survives only as two outbound/inbound edges that share the config in `adapters/tgbot/config.py`: the `TelegramNotifier` (`adapters/tgbot/notifier.py`) that pushes notifications through the Bot API via `TelegramApiClient` (`adapters/tgbot/client.py`, a thin `httpx2` wrapper provided at APP scope in `main/ioc/telegram.py`), and Telegram as an OAuth login/link provider (`presentation/web/routes/auth/oauth.py`). Neither runs a bot process: only `sendMessage` is called, so it needs a valid token but nothing long-lived. The token is part of the Bot API URL path, which is why the `httpx2` logger is held at WARNING.
- **Scheduled jobs (`presentation/faststream/schedules/`)**: the periodic jobs (`sync_tcloud`, `sync_cosplay2`, `outbox_retention`, `notification_retention`) are NATS JetStream message schedules ([ADR-0046](adr/0046-nats-message-schedules-replace-apscheduler.md), [NATS ADR-51](https://github.com/nats-io/nats-architecture-and-design/blob/main/adr/ADR-51.md)), not an in-process scheduler. On startup the worker writes each configured schedule to `scheduler.schedule.<job>` in the dedicated `scheduler` stream (`jstream.py` says why it can't share the event stream) and purges disabled ones; the server then publishes a tick to `scheduler.tick.<job>` on every fire, and a durable per job (`routes/scheduled_jobs.py`) resolves the interactor in the message's REQUEST scope. The stream keeps one message per subject, so a worker that was down runs each job once on return, and a failed run is retried on the usual backoff until the next tick replaces it. Schedules are cron strings in config (`SCHEDULER__*_CRON`: five-field crontab, NATS's six-field form, or `@daily` / `@every 1h`; app timezone); unset = job disabled. Change a schedule by editing `.env` and running `docker compose restart worker` — no code change. The two sync jobs resolve `ExecuteTicketsSync` / `ExecuteCosplaySync` (not the bare sync interactors) so a scheduled run is recorded like any other; see "Anti-corruption layers" above. Trigger a sync without a shell from the web app (needs `sync:run`): Cosplay2 from **Инструменты → Синхронизация**, TicketsCloud from **Инструменты → Билеты**, or from the server via `docker compose run --rm api cli sync tcloud`.
- **Exception Mapping**: Interactors raise pure domain exceptions; the presentation layer catches and maps them to client-safe responses (handlers in `presentation/web/exceptions.py`, registered by `add_exception_handlers`; every error body is RFC 9457 problem details, `ProblemDetails` built by `problem_response()`; [ADR-0044](adr/0044-errors-as-rfc-9457-problem-details.md)).
  - **Unexpected errors become `INTERNAL_ERROR` 500 inside the middleware stack.** The `CatchUnexpectedErrorsMiddleware` (`presentation/web/middlewares.py`) is registered first, so it sits inside CORS, caching, security headers and the request id, and its 500 passes back through them. An `Exception` handler alone would not do: Starlette runs it in `ServerErrorMiddleware`, outside every other middleware, so that response carried no CORS or `X-Request-ID` (a cross-origin browser saw a network error). The `Exception` handler stays only as the last resort for an error raised by an outer middleware. The 500 is logged at ERROR, which is what reaches Sentry.
  - **The HTTP handler is registered on Starlette's `HTTPException`**, not FastAPI's subclass, so the router's own 404 (unknown path) and 405 answer as problem details too ([FastAPI: Handling Errors](https://fastapi.tiangolo.com/tutorial/handling-errors/)).
  - **Status codes via semantic markers, not a leaf registry.** Domain exceptions carry an HTTP-agnostic _marker_ base from `core/exceptions/base.py` — `ConstraintViolation` (400), `NotFound` (404), `Conflict` (409), `RateLimited` (429), `AccessDenied` (403), `UpstreamServiceError` (502, an external provider we call out to failed) — plus `AuthenticationError` (401) from `core/exceptions/auth.py`. `EXCEPTION_STATUS_MAP` keys on those markers only; `_resolve_status_code` walks the exception MRO to find one. **To add an exception, inherit the marker that fits its meaning** (listed _first_ in the bases so it wins MRO precedence over the feature-grouping base, e.g. `class UserNotFound(NotFound, UserException)`) — do not edit the status map. Markers stay HTTP-free so `core/` remains pure (import-linter still passes).
  - **Drift guard**: `tests/unit/presentation/test_exception_status_map.py` enumerates every concrete `AppException` subclass and fails if one resolves to 500 without being listed in its `INTERNAL_ONLY` set (exceptions that never reach an HTTP client — notification delivery, the cooldown guard, missing-vendor-config). If one does reach a client anyway, `app_exception_handler` answers it like any unexpected error — a logged `INTERNAL_ERROR` 500 — so its code and details never leak. Adding an unmarked, non-internal exception breaks this test by design.
  - **Browser-navigation routes opt out.** The OAuth routes (`routes/auth/oauth.py`, `routes/current_user/connections.py`) are entered by a top-level navigation, not a `fetch`, so a problem details body would be _rendered as the page_ — the user reads `{"code": "INTERNAL_ERROR"}`. They must never reach the handlers above: each one catches broadly and leaves as a redirect carrying an `oauthLoginError`/`oauthLinkError` code the SPA turns into a toast. `presentation/web/oauth.py` holds the shared `fetch_telegram_claims`, which translates every failure into an `OAuthFailed` carrying that code. **Do not narrow those `except Exception` clauses**: Authlib raises three unrelated exception families out of one call and only `OAuthError` descends from the obvious base — `httpx` errors escape the token exchange and the JWKS fetch, `joserfc` errors escape ID token validation, and a token endpoint answering `{"error": ...}` raises `OAuth2Error`, a _sibling_ of `OAuthError`. `tests/unit/presentation/test_oauth.py` pins each family.
  - **One callback, two intents, one provider each.** Login and linking share `/auth/oauth/{provider}/callback`; which flow is running comes from an `intent` in Authlib's state payload — server-side, bound to the signed session cookie, single-use — and **never** from a query param or from whether a session cookie happens to be present. Two rules follow and are load-bearing: a `link` intent whose session is missing or belongs to a different user than the `initiator_user_id` recorded at the start must **fail, never fall back to logging in** (that fallback is an account-takeover path), and the `{provider}` segment must stay in the URL. The latter is RFC 9700 §4.4.2.2 — a distinct redirect URI per issuer — which is this app's mix-up defence because Telegram does not advertise `authorization_response_iss_parameter_supported`, so RFC 9207's preferred `iss` response parameter is unavailable. The state also carries the `issuer` (§4.4.2 requires storing it per request and binding it to the user agent) and the callback compares it back before the token exchange. Rationale: [ADR-0012](adr/0012-single-oauth-callback-keyed-on-the-oidc-subject.md).
  - **Client-facing code set**: `presentation/web/error_codes.py` derives the codes a client can actually receive (exceptions that resolve to a marker, plus the synthesized `VALIDATION_ERROR`/`HTTP_ERROR`/`INTERNAL_ERROR`). The OpenAPI generator stamps them onto `ProblemDetails.code` as an `enum`, so the frontend gets a typed union and can compile-time-check its error copy is complete (see [api.md](api.md)). The test above reuses the same module — one source of truth for "which exception maps where".

## Logging & Observability

- **Setup**: Logging is configured once per process by `setup_logging()` in `adapters/debug/logging.py`, called from the shared `main/common.py:init()` that every service entrypoint runs. It uses **structlog as a formatting layer over the stdlib `logging`** module (via `ProcessorFormatter` + `foreign_pre_chain`), so plain `logging.getLogger(__name__)` records and structlog records flow through the same pipeline. `setup_logging()` is idempotent — it clears existing root handlers before adding its own, so calling `init()` more than once does not duplicate log lines.
- **Getting a logger**: Use the stdlib pattern everywhere: `logger = logging.getLogger(__name__)` at module level. Do not call `structlog.get_logger()` — the codebase standardises on stdlib loggers.
- **Output format**: Console (`ConsoleRenderer`) by default; JSON (`JSONRenderer`) when `DEBUG__JSON_LOGS=true`. Log level and JSON toggle come from `DebugConfig` (`adapters/debug/config.py`).
- **Environment posture (`APP_ENV`)**: `APP_ENV=dev|staging|prod` is the single source of truth for the debug posture. It's read via `Field(validation_alias="APP_ENV")` (the Python attribute stays `config.env`) — named `APP_ENV` rather than bare `ENV` because pydantic-settings also reads `os.environ`, where a stray ambient `ENV` could silently shadow the `.env` value. `DebugConfig` ships **production-safe defaults** (`enabled=False`, `logging_level=INFO`, `json_logs=True`); `EnvConfig._apply_environment_posture` relaxes them to developer-friendly values (`enabled=True`, `DEBUG`-level, console logs) **only when `APP_ENV=dev`** and the specific `DEBUG__*` var wasn't set explicitly (an explicit value always wins). With `APP_ENV=prod` the app **refuses to start** if `DEBUG__ENABLED=True`, since FastAPI debug mode leaks stack traces in HTTP responses. So leave the derived flags unset in `.env` and just set `APP_ENV`.
- **Structured logging convention**: The processor chain runs `ExtraAdder()`, so anything passed via the stdlib `extra={...}` dict is captured and rendered as top-level fields (queryable in the JSON renderer). Follow these rules when adding log calls (especially in interactors):
  - **Short, static message + fields in `extra`.** Keep the message a fixed human-readable string and put identifiers in `extra` — do not interpolate values into the message _and_ repeat them in `extra`. Prefer `logger.info("Subscription created", extra={...})` over `logger.info("Subscription %s created", id, ...)`.
  - **Discrete scalar fields, not whole objects.** Never pass a domain model/dataclass as an extra value — the JSON renderer falls back to `repr`, producing one unqueryable blob and risking unintended field/PII leakage. Pass the specific ids/flags you need instead.
  - **Stringify UUID ids.** `extra` values that are `UUID`-based VOs must be wrapped in `str(...)`; a raw `UUID` renders as `"UUID('…')"` under the JSON renderer. Plain ints/bools/strings need no conversion.
  - **Alertable event names.** When a log line marks an outcome someone may alert on, add a fixed machine-readable name alongside the message — the outbox relay uses `relay_event` (`published`, `publish_failed`, `publish_stuck`, `tick_failed`, `listener_lost`, `listener_failed`) so a log query needs no message parsing. Never use the key `event`: structlog renders the log message under `event`, and `ExtraAdder` would overwrite it.
  - **Consistent key names.** Use `actor_id` for the authenticated user performing the action; when a separate subject exists, name it explicitly (e.g. `target_user_id`). Name entity ids by their type (`subscription_id`, `event_id`, `mailing_id`, …).
  - **Verbosity & secrets.** Log one record per significant state change (typically after `commit`); do not log reads/queries. Log security-relevant auth events (login success/failure with a `reason`, lockouts). Never log passwords, OTP/login codes, raw emails, or other PII — `client_ip` is acceptable on failed/blocked logins for abuse correlation.
  - **Secret fields stay out of reprs.** A Pydantic field holding a password or one-time code sets `repr=False` (see `PASSWORD_FIELD` in `core/vo/fields.py`). Sentry records each frame's local variables by their repr and its scrubber matches variable names only, so a plain field would ship the secret with any unexpected error; `tests/unit/application/test_secret_fields_repr.py` lists the models it guards.
- **Request correlation**: The web app binds a `request_id` into structlog `contextvars` for every HTTP request via `BindRequestContextMiddleware` (`presentation/web/middlewares.py`, registered last in the factory so it runs outermost). Because the processor chain includes `merge_contextvars`, every log line emitted while handling a request automatically carries that `request_id`; it is also echoed back in the `X-Request-ID` response header (and reused from the incoming header when it is up to 128 characters of `[A-Za-z0-9._-]`; anything else is replaced, since the value is client-controlled and lands in every log line). To attach more fields to all logs in a scope, use `structlog.contextvars.bind_contextvars(...)`.
- **FastStream integration**: FastStream (the `stream` service) does **not** use its default logger — that one installs its own colorized handler with `propagate=False` and a fixed `INFO` level, which would bypass structlog and emit plaintext even under `DEBUG__JSON_LOGS=true`. Instead `get_stream_logger()` (`presentation/faststream/logger.py`) hands the broker and `FastStream` app a plain stdlib `logging.getLogger("faststream")` with its handlers cleared and `propagate=True`, so framework/access logs and the `Logger` dependency injected into subscribers all flow through the root structlog handler (correct format + level). FastStream forwards its per-message context (`message_id`, channel) via the record's `extra`, so `ExtraAdder` surfaces it automatically.
- **Noise control**: Noisy third-party loggers (urllib3, httpx2) are raised to WARNING, and `uvicorn.access` logs for the `/debug/health` probe are dropped by `_HealthCheckFilter`.
- **Error reporting (Sentry)**: `setup_telemetry()` (`adapters/debug/telemetry.py`) wires Sentry when `DEBUG__SENTRY_DSN` is set. Expected errors — request validation and every domain exception with a status marker — are filtered out by `is_expected_error` (`presentation/web/exceptions.py`, injected by `main/common.py`); a marker-less domain exception is a bug and is reported, and request headers / user PII are scrubbed before events are sent.
- **Tracing across NATS**: one request's work is one Sentry trace, through the outbox and every consumer. `SentryMiddleware` (`presentation/faststream/middleware.py`, on every broker) stamps `sentry-trace`/`baggage` onto a publish made inside a span (a `queue.publish` span), and each consumed message continues that trace in its own isolation scope as a `queue.process` transaction named after the durable, with the retry count and stream latency Sentry's Queues view reads ([Sentry: Queues module](https://docs.sentry.io/platforms/python/tracing/instrumentation/custom-instrumentation/queues-module/)). Outbox events cross a gap no header survives — the relay publishes later, from a background task, outside any trace — so `uow.commit()` stores the writer's headers in `outbox_events.trace_headers` and the relay forwards them (the middleware keeps headers already on a message). Only an active span is propagated (`adapters/debug/tracing.py:current_trace_headers`): outside one, the scope's fallback trace id would stitch every relay-sent message into one trace. Sampling follows the producer's decision, so a sampled flow stays whole.

## Dead-code sweep (vulture)

- **`just backend-deadcode`** runs [vulture](https://github.com/jendrikseipp/vulture) over `src/fanfan`. It finds _globally_ unused code — a function, class or import nothing references anywhere — which ruff's rules can't: ruff's `F401`/`F841` are _local_ (unused within one scope), the high-signal slice we already gate on. Vulture adds the cross-module slice, which is inherently lower-signal.
- **Manual aid, not a gate.** Deliberately out of `backend-lint` and CI. This app is framework-driven — Dishka providers are resolved by reflection, FastAPI/FastStream handlers are dispatched by their routers, Pydantic/adaptix DTO fields are populated during (de)serialisation — so a static pass sees much of it as "unused". A blocking gate on that is noise; the sweep is for a human to read.
- **Config** is `[tool.vulture]` in `backend/pyproject.toml`: `min_confidence = 80` (drops the 60%-confidence attribute guesses that flood on DTO/ORM fields), `exclude` skips the Alembic `migrations/` tree (env.py hook signatures and autogenerated revisions are framework contracts), and `ignore_decorators` quiets the routers (`@*_router.*`), DI (`@provide`, `@inject`), Click, Pydantic validators and `@declared_attr`.
- **`vulture_whitelist.py`** holds the residue a decorator/name rule can't express — currently imports used only inside `cast("<Name>", …)` string literals, which ruff resolves but vulture can't see into. Extend it with `uv run vulture src/fanfan --make-whitelist`, then keep only genuine false positives — never paste real dead code in to silence it.

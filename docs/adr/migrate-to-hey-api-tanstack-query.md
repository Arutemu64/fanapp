# Migrate from openapi-typescript + openapi-fetch to hey-api (and evaluate TanStack Query)

**Status**: Proposed
**Date**: 2026-09-15

## Context

The frontend fetches data via `openapi-fetch` (typed wrapper around `fetch()`) with types generated by `openapi-typescript` through a custom `scripts/generate-api.mjs` (needed for the `format: "binary"` → `Blob` transform). Offline caching is hand-rolled in `src/lib/utils/offlineCache.ts`: network-first with IDB fallback, user/universal scope separation, cache warming, `cachedAt` envelopes.

Two separate questions were raised:

1. **Should the codegen + client move to `@hey-api/openapi-ts`?** — yes, see PR 1.
2. **Should client caching move to TanStack Query?** — much less clear once the app's real invalidation architecture is accounted for. See the review below and PR 2's options.

## Decision

**PR 1 (recommended, ready to implement):** swap codegen and client to hey-api. Mechanical, compiler-verified, no behavior change.

**PR 2 (not ready — decide between options first):** the TanStack Query migration as originally scoped was a ~4× undercount. The app's invalidation architecture is a deliberate, well-documented system built on SvelteKit's load graph; replacing it is a much larger project than "migrate 5 cached endpoints". Three options are laid out below with honest cost/benefit.

## Review: the app's invalidation architecture

This section is the prerequisite for judging PR 2. It was not accounted for in the original plan.

### Dependency keys

Ten `depends()` keys, ~20 keyed `invalidate()` call sites, plus two `invalidateAll()` paths.

| Key | Declared in | Invalidated by |
|-----|-------------|----------------|
| `app:current-user` | `+layout.ts:23` | `lib/api/index.ts:56` (401 middleware), `profile/+page.svelte:58` |
| `app:config` | `(app)/+page.ts:15` **and** `(app)/voting/+layout.ts:12` | `(app)/+page.svelte:24`, `voting/+layout.svelte:39,51` |
| `app:schedule` | `schedule/+page.ts:19` | `schedule/+page.svelte:146`, `SubscribeModal:55`, `UnsubscribeModal:47`, `EventCard:121`, `MoveEventModal:85`, `import_schedule/+page.svelte:69` |
| `app:schedule:changes` | `schedule/changes/+page.ts:23` | `changes/+page.svelte:33`, `ScheduleChangeCard:42` |
| `app:notifications` | `(app)/+layout.ts:19` **and** `notifications/+page.ts:15` | *(no keyed invalidation — refreshed via `invalidateAll`)* |
| `app:voting:nomination` | `voting/[nominationCode]/+page.ts:10` | `voting/[nominationCode]/+page.svelte:53` |
| `app:broadcasts` | `tools/broadcast/+page.ts:13` | `broadcast/+page.svelte:119`, `BroadcastHistory:95` |
| `app:sync-sources` | `tools/sync/+page.ts:10` | `sync/+page.svelte:85,94` |
| `app:festival-settings` | `tools/settings/+page.ts:19` | `settings/+page.svelte:167` |

Two keys (`app:config`, `app:notifications`) are declared by **more than one load**, so a single `invalidate()` fans out to several loads. TanStack Query models this with prefix-matched key hierarchies — it maps, but the hierarchy has to be designed deliberately, not derived from operation IDs.

### `invalidateAll()` paths

| Site | Trigger | Why |
|------|---------|-----|
| `lib/utils/auth.ts:53` | After login (`goto(..., { invalidateAll: true })`) | Every load must re-run under the new identity |
| `lib/utils/reconnectRefresh.ts:35` | SSE reconnect / offline→online / tab foreground | Catch-up refetch for changes missed while disconnected |

`reconnectRefresh.ts` is a leading+trailing debounce (3s window) that deliberately collapses a burst of recovery signals — the `online` edge and the SSE re-handshake routinely fire together — into one refresh, and caps a flapping connection at one refresh per window. Its module-scoped state is documented as an intentional shared rate-limit clock, not session state.

### Load-function responsibilities beyond fetching

Every load does more than fetch. Any migration must preserve each of these:

| Responsibility | Where | Notes |
|---|---|---|
| **`await parent()` identity graph** | Most loads | Pull `user` from the root layout load |
| **`error(403, …)` permission guards** | `schedule/changes`, `broadcast`, `sync`, `settings`, `notifications` | Route-level authorization via SvelteKit's error boundary, with Russian copy |
| **`error(503, …)` online-failure** | `schedule/+page.ts:55`, `notifications/+page.ts:57` | Hard error when reachable but failing |
| **Offline degradation branch** | `schedule/+page.ts:46`, `notifications/+page.ts:47` | Returns `offlineMiss: true` for a calm inline state instead of an error |
| **`stale` / `cachedAt` passthrough** | `schedule`, `notifications` | Drives the "synced at …" UI |
| **Client-side join** | `schedule/+page.ts:96` `mergeSubscriptions` | Merges two endpoints into `ScheduleEventWithSubscription` |
| **Streaming to avoid a waterfall** | `(app)/+layout.ts:21` | Returns an *unresolved* promise so the shell paints before `/me` + 2 more round-trips |
| **Pending-logout short-circuit** | `+layout.ts:30` | `isLogoutPending()` returns guest without any request |
| **Reachability-aware skipping** | `voting/+layout.ts:17`, `voting/[nominationCode]:15`, `(app)/+layout.ts:35` | Skip doomed requests when known offline |

### Hard incompatibility: the `undefined` sentinel

`fetchWithCache`'s contract uses three states:

- a **value** → cache it, return it fresh
- **`null`** → a real cached value (authoritatively logged out)
- **`undefined`** → "reachable but no usable verdict" → keep the last-good cached copy

`+layout.ts:57` relies on this for session safety: a 5xx or parse error on `/me/` must **not** downgrade a logged-in user to guest, because that would orphan their per-user caches on a shared device.

**TanStack Query throws `Query data cannot be undefined` when `queryFn` returns `undefined`.** The nearest equivalent is to throw and rely on the query keeping its previous data — which is semantically different (it flips `isError`, affects retry, and interacts with `networkMode`). This is load-bearing session logic and needs a verified design, not a one-line port.

## PR 1 — Swap to hey-api

**Goal**: replace `openapi-typescript` + `openapi-fetch` with `@hey-api/openapi-ts` across the codebase. Zero behavior change. `offlineCache.ts`, `depends`/`invalidate`, SSE and reachability all stay exactly as they are.

### Why one shot is safe here

The transform is mechanical — path-string calls become named SDK functions, type imports point at the new output. `svelte-check` surfaces every unmigrated call site as a type error, so the compiler says when you're done. The spec's 62 operations all carry clean snake_case `operationId`s (`get_current_user`, `list_oauth_providers`), so hey-api's generated names will be predictable camelCase, not FastAPI's mangled defaults.

### Verify before starting

Two assumptions must be confirmed against current hey-api docs, because the codebase depends on both:

1. **Per-call `fetch` override.** Loads pass SvelteKit's tracked fetch: `client.GET('/me/', { fetch, signal })`. Confirm hey-api SDK functions accept a per-call `fetch`. (Lower stakes than it looks — `ssr = false`, so there's no SSR response inlining to preserve — but the pattern is deliberate.)
2. **Client instantiation.** Current code calls `createApiClient()` **fresh per load**, and `+layout.ts:80` spins a separate `warmClient` specifically so warming isn't tied to the load's tracked fetch. hey-api's idiomatic pattern is a module-level singleton via `client.setConfig()`. AGENTS.md forbids request- or user-scoped state in module singletons. The client holds only `baseUrl` + `credentials` (no user state), so a singleton is arguably fine — but this reverses a deliberate choice and needs an explicit decision, recorded here, rather than a silent drift.

### Steps

1. **Install and configure.**
   - `pnpm add -D @hey-api/openapi-ts` (pin exact — pre-v1)
   - `frontend/openapi-ts.config.ts` → input `shared/openapi/openapi.json`, output `src/lib/api/generated/`
   - Plugins: `@hey-api/typescript`, `@hey-api/sdk`
   - Blob handling is native; the `generate-api.mjs` transform is no longer needed

2. **Run codegen and inspect.** Verify types match `schema.d.ts` semantically and every operation produced a named SDK function.

3. **Port middleware to interceptors.**
   - `reachabilityWatch` → response interceptor calling `markReachable(!isBackendUnreachableStatus(status))`; error interceptor calling `probeReachability()`
   - `sessionExpiryWatch` → response interceptor: on 401, outside `CREDENTIAL_CHECK_PATHS`, debounced `invalidate('app:current-user')`
   - Preserve the `CREDENTIAL_CHECK_PATHS` exclusions and the `reconcilingSession` latch — both carry comments explaining non-obvious constraints
   - Verify manually: expired session, wrong password, backend down

4. **Migrate all 68 call sites.**
   ```ts
   // Before
   const { data, error } = await client.GET('/schedule/events/{id}', {
     params: { path: { id: eventId } }, signal
   });

   // After
   const { data, error } = await getScheduleEvent({ path: { id: eventId }, signal });
   ```

   | Area | Files | ~Calls |
   |------|-------|--------|
   | `(app)/schedule/**` | 8 | 10 |
   | `(app)/voting/**` | 4 | 5 |
   | `(auth)/login/**` | 3 | 4 |
   | `(app)/(protected)/tools/**` | 10 | 12 |
   | `(app)/(protected)/profile/**` | 6 | 12 |
   | `(app)/(protected)/notifications/**` | 3 | 6 |
   | `(app)/components/**` | 3 | 5 |
   | Root layouts/pages | 4 | 8 |
   | Services/utils (`lib/`) | 8 | 6 |

5. **Remove local type aliases.** openapi-typescript's nested `components['schemas'][…]` access forced ~15 local aliases across 10 files; hey-api exports types directly, so they become pointless indirection.

   | File | Aliases |
   |------|---------|
   | `lib/utils/permissions.ts` | `Permission` |
   | `lib/data/socialProviders.ts` | `SocialProvider` |
   | `lib/api/errors.ts` | `ApiErrorCode` (nested `ErrorMessage['code']` — may need to stay if hey-api doesn't export the nested member type) |
   | `lib/constants/festival.ts` | `PublicConfig` (`PublicConfigDTO`) |
   | `(auth)/login/+page.svelte`, `+page.ts` | `SocialProvider` |
   | `tools/voting/+page.svelte` | `NominationContender`, `Winner` (`UserBaseDTO`) |
   | `tools/broadcast/+page.ts` | `Mailing` (`MailingDTO`) |
   | `tools/broadcast/BroadcastHistory.svelte` | `Mailing`, `MailingStatus`, `UserRole` |
   | `tools/sync/+page.svelte` | `SyncSourceStatus`, `SyncSource`, `SyncRunStatus` |

   Keep a rename where it carries domain meaning at the use site (`Winner` for `UserBaseDTO`); otherwise use the generated name.

   Note `src/lib/types/*.ts` (`schedule.ts`, `user.ts`, `voting.ts`, `notifications.ts`, `feedback.ts`, `participant.ts`, `nominations.ts`) are re-export modules over the same schema — they're the intended indirection layer and can stay, just repointed at the new import.

6. **Update build tooling.**
   - `package.json`: `generate-api` calls `openapi-ts`
   - Justfile `frontend-generate-api`: `pnpm openapi-ts`
   - Justfile `frontend-check-api`: hey-api has no `--check` flag, so use regenerate-then-diff:
     ```just
     frontend-check-api: backend-generate-openapi
         cd frontend && pnpm openapi-ts && git diff --exit-code src/lib/api/generated/
     ```
     The two-layer drift gate is preserved: the backend pytest guards `openapi.json` ↔ app; this guards `openapi.json` ↔ generated client. Verify hey-api's output is deterministic (stable key ordering) before relying on the diff.

7. **Delete.** `scripts/generate-api.mjs`, `src/lib/api/schema.d.ts`; rewrite `src/lib/api/index.ts` as the hey-api client config + interceptors.

8. **Remove deps.** `pnpm remove openapi-typescript openapi-fetch`

9. **Gates + smoke test.** `just frontend-lint && just frontend-check`. Manually: login, schedule, vote, go offline and back, expire a session.

**Deliverable**: every API call on hey-api SDK; old codegen gone; behavior identical; gates green.

### Explicitly unchanged by PR 1

`offlineCache.ts`, `reachability.ts`, `reconnectRefresh.ts`, all `depends()`/`invalidate()` call sites, SSE, the service worker. Only the call syntax and type imports move.

## PR 2 — Client caching: three options

The original plan assumed TanStack Query replaces `offlineCache.ts` and that's that. The review above shows the real coupling: ~30 invalidation call sites, 5 permission guards, 2 error-boundary branches, a streaming load, a client-side join, and one hard `undefined` incompatibility.

Decide between these before writing code.

### Option A — Do nothing (make `fetchWithCache` cache-first)

The actual complaint driving this is **network-first paint**: online users wait for a round-trip before seeing content. That can be fixed inside the existing file — return the cached copy immediately, revalidate in the background, and let the existing `invalidate()` paths pick up the fresh value.

- **Cost**: ~30 lines in `offlineCache.ts`, plus a way for the background revalidation to push its result to the page (the simplest is to keep the current shape and just reorder, accepting one extra render).
- **Keeps**: every guard, every invalidation, the `undefined` sentinel, `stale`/`cachedAt`, offline degradation.
- **Loses**: nothing. No new dependency, no bundle cost.
- **Doesn't get**: per-component loading states, request deduplication, automatic GC.

### Option B — TanStack Query *inside* load functions

Keep `depends`/`invalidate` and the load graph. Use `queryClient.fetchQuery()` inside each load where `fetchWithCache` is called today, and let TanStack Query own caching + IDB persistence.

- **Cost**: 5 load functions rewritten; a persister; the `undefined` sentinel still needs re-expressing.
- **Keeps**: all permission guards, all error branches, all ~30 invalidation call sites unchanged, `reconnectRefresh`'s `invalidateAll`.
- **Gains**: stale-while-revalidate, dedup, GC, a maintained cache layer instead of a bespoke one.
- **Doesn't get**: per-component `isPending` / `isError` — data still arrives via `load` → `$page.data`.

### Option C — Full TanStack Query (components own their queries)

What the original plan described. Load functions shrink to guards only; components call `createQuery`.

- **Cost**: the whole review section above. ~30 invalidation sites → `invalidateQueries`; 5 `error(403)` guards need a new home (they can stay in slimmed loads); `error(503)` / `offlineMiss` branches become per-component states; `stale`/`cachedAt` → `isStale` / `dataUpdatedAt`; `mergeSubscriptions` → a derived combining two queries; the streaming load in `(app)/+layout.ts` becomes two independent queries (TanStack handles this better, but it's a rewrite); `reconnectRefresh` → `queryClient.invalidateQueries()`; login's `invalidateAll` → `queryClient.clear()`; plus the `undefined` sentinel.
- **Gains**: per-component loading/error states, the full plugin ecosystem, auto-generated hooks via `@hey-api/tanstack-query`, one consistent data-fetching model.
- **Realistically**: 3–5 PRs, not one. Slice by route group, with the schedule vertical first as the pattern prototype.

### Recommendation

**Option A or B.** The existing architecture is deliberate and documented — the offline degradation, the reachability-aware skipping, the three-state session verdict, the debounced reconnect catch-up are all behaviors that took thought and that TanStack Query does not provide for free. Option C trades a working system for a more conventional one, and the stated pain (cache-first paint) doesn't require it.

Pick Option C only if a *new* requirement appears that the load graph genuinely can't serve — infinite scroll with cursor pagination, optimistic mutations, polling with per-component state. Note `lib/utils/feed.ts` already hints at pagination pressure; if paginated feeds are on the roadmap, that strengthens the case for C.

### If Option C is chosen

Sequence, one PR each: (1) infra — `QueryClientProvider`, IDB persister, key hierarchy design, `@hey-api/tanstack-query` plugin; (2) schedule vertical as the prototype, including `mergeSubscriptions` and the offline branch; (3) voting + notifications; (4) tools routes; (5) root layout, session handling and `reconnectRefresh` last, since they're the riskiest.

Design the key hierarchy up front so the fan-out keys work: `['universal','schedule']`, `['user','notifications']`, etc., with `invalidateQueries({ queryKey: ['user'] })` for logout and prefix matching reproducing today's multi-load `depends()` fan-out.

## Risks

| Risk | Applies to | Mitigation |
|------|-----------|------------|
| hey-api is pre-v1 | PR 1 | Pin exact version; codegen is a build step, easy to revert |
| Per-call `fetch` override unsupported | PR 1 | Verify before starting; `ssr = false` limits the blast radius |
| Module-singleton client vs AGENTS.md rule | PR 1 | Client holds no user state; record the decision explicitly |
| hey-api output nondeterministic → false drift failures | PR 1 | Verify stable ordering before adopting the git-diff gate |
| `undefined` sentinel has no TanStack equivalent | PR 2 B/C | Design and test the throw-based equivalent against session-expiry cases |
| ~30 invalidation sites | PR 2 C | Slice by route group; design the key hierarchy first |
| Permission guards lose the error boundary | PR 2 C | Keep slimmed `load` functions for `error(403)` |
| Offline degradation branches | PR 2 C | Re-express per component; test with the backend down |
| Bundle +15–20kb | PR 2 B/C | Acceptable for a PWA; partially offset by deleting `offlineCache.ts` |

## Out of scope

- Backend changes — the OpenAPI spec is unchanged.
- SSE architecture.
- Service worker fetch strategy (it does **not** use `idb-keyval` — confirmed; that dependency belongs solely to `offlineCache.ts`).
- Optimistic mutations.

**Remove (PR 1):** `openapi-typescript`, `openapi-fetch`

## Overall Impression

The bones are solid: the card grid → nomination detail → vote flow is correct, state is communicated, and the code is tidy. The biggest immediate problem is a trust failure: "Проголосовать" on a card that navigates sets the wrong expectation, and guidance copy that ignores `canVote` tells users to do something they cannot. Fix those two and the UX becomes markedly more honest. The search container nested-card is the most visible visual debt; everything else is polish.

---

## What's Working

1. **Voted-state communication**: Green ring + badge on both NominationCard and ParticipantCard is a strong, dual-signal affordance. A user who has voted can see their vote at a glance — from the list level AND from inside the nomination.
2. **Cancel-vote pattern**: The Отменить button on a voted ParticipantCard is the right call — it treats the vote as reversible without a confirmation dialog overhead, which matches the convention context.
3. **VotingStatusAlert for blocked states**: The yellow/red alert for `no_ticket`, `not_authenticated`, and `disabled` explains exactly why voting isn't available and matches the design system's Notice pattern correctly.

## Priority Issues

**[P1] NominationCard CTA label creates false affordance**
- **What**: NominationCard footer shows `<CheckOutline /> Проголосовать` for unvoted nominations. The whole card is `href="/voting/{nomination.code}"` — clicking navigates. "Проголосовать" is a verb that implies the action is casting a vote, not going to a page.
- **Why it matters**: A first-time user taps "Проголосовать", lands on a new page with more cards, and has to orient. The expectation was "I voted," the reality is "I navigated." Erodes trust in the interface, especially for a teen at a noisy convention who just wants to vote quickly.
- **Fix**: Change the CTA to "Открыть" with `<ArrowRightOutline />`, or simply "Голосовать →". Save "Проголосовать" for the actual vote button on ParticipantCard where the action matches the label. When the nomination already has a vote, the existing "Перейти" label is correct — align the unvoted state to the same pattern.
- **Suggested command**: `/impeccable clarify voting route`

**[P1] Guidance copy ignores `canVote` — instruction conflicts with reality**
- **What**: In `[nominationCode]/+page.svelte`, the subtitle shows "Выбери участника, чтобы отдать голос" whenever `!hasVoted`, regardless of `canVote`. When voting is closed (`disabled`), the user has no ticket (`no_ticket`), or isn't logged in (`not_authenticated`), they see an instruction they literally cannot follow — all vote buttons are disabled.
- **Why it matters**: The copy makes the interface feel broken. User reads "pick a participant to vote" → tries to tap → button is disabled → confusion. For a convention attendee who shows up without a ticket, this is a credibility hit.
- **Fix**: The subtitle condition should be `{#if hasVoted}` / `{:else if canVote}` (show the instruction) / `{:else}` (show nothing, or a brief "голосование недоступно" — the alert above already explains why). One-line fix in `[nominationCode]/+page.svelte`.
- **Suggested command**: `/impeccable clarify voting route`

**[P2] VotingStatusAlert on the "open" state is decorative noise**
- **What**: `VotingStatusAlert` renders a green "Голосование открыто. Ты можешь голосовать за участников." banner on BOTH the nomination list page AND each nomination detail page whenever voting is open. This is the happy path — it triggers on every single visit.
- **Why it matters**: The design system's Color-Earns-Its-Place Rule states saturated color appears only on action, active state, or semantic state. A green banner permanently decorating every voting screen is the exact opposite — it's a semantic state (success/info) used as wallpaper. It also pushes the actual nominations grid further down the page. The warning states (`disabled`, `no_ticket`, `not_authenticated`) are exactly right; open doesn't need it.
- **Fix**: In `VotingStatusAlert`, add `{#if votingState && votingState.status !== 'open'}` so the banner only renders for non-default states. Or keep the `open` case but downgrade it to a minimal inline tag rather than a full-width alert.
- **Suggested command**: `/impeccable distill voting route`

**[P2] Search input wrapped in a standalone card — nested cards**
- **What**: In `[nominationCode]/+page.svelte`, the `<Search>` component is wrapped in a `<div class="... rounded-2xl border border-gray-200 bg-white p-3 shadow-sm ...">`. The search input already has its own Flowbite border and background. The wrapper is a card inside a page that already uses cards — nested cards.
- **Why it matters**: "Nested cards are always wrong" is an absolute ban. The container creates a visual double-border and elevates the search bar to the same visual hierarchy as a nomination card, which is wrong. It also adds a `shadow-sm` on a non-floating, non-tappable element — another violation.
- **Fix**: Remove the wrapper `<div>`. Apply `class="mb-4"` directly on `<Search>`. If more breathing room is needed, add a subtle `bg-gray-50 dark:bg-gray-900` tint to the whole search row without the card container.
- **Suggested command**: `/impeccable polish voting route`

**[P2] Empty search-results state gives no escape**
- **What**: When no participants match the search query, the empty state shows `<UsersGroupOutline />` + "Участники не найдены" — no clear-search link, no "X" affordance to reset (though the clearable prop exists on Search). The user may not realize a simple tap on the ✕ clears the search.
- **Why it matters**: The search ✕ button is the only affordance, but it's easy to miss, especially one-handed. A confused user may think the nomination genuinely has no participants.
- **Fix**: Add a "Очистить поиск" link or button inside the empty state, wired to `searchQuery = ''`.
- **Suggested command**: `/impeccable harden voting route`

## Persona Red Flags

**Casey (Distracted Mobile User)** — *primary persona, teen at a convention, one-handed*:
- ParticipantCard vote button ("Голосовать") sits in the bottom-right corner of each card. On phones wider than ~390px, that's the hardest corner to reach one-handed. The thumb zone on a standard phone peaks at the bottom-center and bottom-left — not the right. In a grid of 2 columns, the right column's action button is a stretch.
- "Проголосовать" CTA on NominationCard navigates to a new page — Casey taps, gets teleported, disoriented. At a loud convention, this causes re-orientation time and possibly a back-tap.
- No persistence on interrupted flow. If Casey locks their phone mid-search (common at conventions), returns, and the page reloads, the search query is gone. Acceptable given server-side rendering, but worth noting as a friction point.

**Jordan (Confused First-Timer)** — *voting for the first time, needs every step to be obvious*:
- "Проголосовать" on a card that navigates will confuse Jordan. They will tap expecting to vote, see a new page, and wonder what just happened. No explanation that voting requires selecting a specific participant.
- After voting, the nomination card shows "Голос учтён" badge — clear. But Jordan doesn't know if they can vote in OTHER nominations (no cross-nomination summary anywhere). They may think voting in one nomination is the whole task.
- "Выбери участника, чтобы отдать голос" shows when voting is closed — Jordan will try anyway and find all buttons disabled. The mismatch between instruction and reality is a P1 trust failure for this persona.

**Convention Attendee: "Саша"** — *project-specific persona, Russian teen, first FAN FAN visit, light phone user*:
- Profile: 16-17 years old, using the app for the first time at the convention. Primarily phone-native but not app-savvy. Came to vote for their favourite cosplayer. Reads Russian fluently; English labels would be blockers.
- Behaviors: Reads every on-screen instruction literally. Gets nervous if buttons are greyed out without explanation. Will share their screen with friends to figure out problems.
- Red flags: The subtitle "Выбери участника, чтобы отдать голос" when voting is disabled. Vote count displayed during active voting may cause Саша to skip unpopular participants even if they genuinely prefer them (bandwagon effect). No explanation of whether they can vote in multiple nominations simultaneously.

## Minor Observations

- `client-side search`: `searchQuery.toLowerCase()` should be `searchQuery.trim().toLowerCase()`. Leading/trailing spaces in the input produce missed matches. One-character fix.
- `NominationCard` reserves `min-h-6` at the top for the badge — when unvoted, this is just empty vertical space (~24px). Small but consistent waste in a card that's already compact.
- The `toastService.error(error)` calls in ParticipantCard pass raw API error objects. If the API returns a structured error, the toast likely shows `[object Object]` or a JSON blob. Needs a proper error message extractor.
- `nomination.works_url` uses `href` without URL validation — if the backend sends a relative or malformed URL, the button renders but breaks. Low-risk, worth noting.
- ParticipantCard: when `hasVoted && participant.user_vote === null` (voted for a different participant), no button renders in the card footer. The footer div still renders with the vote count but no action. This is intentional but leaves an asymmetric layout: some cards have a button, some don't. The layout holds but the card weight feels uneven at a glance.
